## Findings

### F1 (major, planner): the KV loop stops at the first KV type that fits, so quantized KV never wins

`internal/fit/fit.go:325` breaks out of the KV loop after the first cache type that fits, with the comment "a smaller KV type at the same ctx would only lose quality". A smaller KV type also changes placement and speed, and on a 12 GB card it is often the difference between split mode and full GPU.

Evidence (RTX 4070 12 GB, 32 GB DDR5, from a temporary `internal/fit` debug test):

| Model | Current planner | With quantized KV |
|---|---|---|
| Nanbeige4.3 33B IQ2_XXS | 8K f16, GPU, effective 10.77 | 32K q4_0, GPU, 10.76 GiB, 11.3 tok/s, effective 16.62 |
| Ternary Bonsai 2 27B Q2_0 | 32K f16, GPU, effective 16.92 | 64K q8_0, GPU, 9.87 GiB, 42.6 tok/s, effective 17.96 |
| Qwen3.8 27B GSQ-RCO-IQ3_XXS | 64K f16 split, 6.0 tok/s, effective 19.80 (slow) | 64K q4_0, GPU, 11.21 GiB, 32.2 tok/s, effective 19.5 |

Effect on this tier: the planner leaves 1-6 effective points and 3-5x speed on the table for the three dense 27-33B models. Fix: try all KV types at each context and compare (or order q4_0/q8_0 before f16), instead of breaking on the first fit. `internal/fit` is T04's area, so this report only records it.

### F2 (major, planner): draft bytes are counted in plans that then disable the draft

`internal/fit/fit.go:339-340` adds the draft size to the resident weights, and `internal/fit/fit.go:476` clears speculative decoding for Split/Hybrid/CPU plans. The draft bytes stay in the layer-split math, so a plan that will not use the draft still pays for it.

Evidence: Qwen3.8 27B with the catalog's 3.16 GB Q8_0 MTP draft (`internal/catalog/catalog.json:199`) is pushed from GPU mode to split mode on a 12 GB card: 8.2 tok/s instead of 54.4. With the 1.68 GB Q4_0 draft it stays on the GPU but drops from 64K to 32K context; with no draft it runs 64K on the GPU at 44.7 tok/s. The tier entry therefore omits the draft. Fix: decide spec before adding draft bytes, or subtract them when spec is cleared.

### F3 (minor, catalog): Gemma 4 31B fits 12 GB only at 2-bit and 16K, because of the sliding-window cache

`internal/catalog/catalog.json:1024`. The IQ2_XXS file is 8.53 GB and the sliding-window cache is ~2.3 GB at any context (50 layers x 16 KV x 256 x 3072 tokens), plus 0.31 GB for the 10 global layers at 8K. The plan fits in split mode at 16K on Linux (11.39 GB GPU + 2.67 GB RAM, ~8 tok/s) and at 32K on the Mac, but the catalog note "Gemma 4 31B: ~1-2 GB" in `internal/fit/fit.go` understates the cache. It is the quality-over-speed vision pick, not a comfortable fit; the QAT Q4 file (17.6 GB) is a 16-24 GB pick.

### F4 (minor, catalog): two 30-35B MoE models have no quants that fit 12 GB

Nemotron 3.5 Lightning 30B A3B's smallest published file is UD-IQ3_XXS at 19.8 GB, and Clover 35B A3B Preview only publishes Q4_0 19.6 GB and up. They are fine 16-24 GB models but cannot serve this tier. If the catalog wants them for 12 GB, it needs IQ2 files.

### F5 (new model): K2 Horizon 7B is missing from the catalog and is the best small dense model for this tier

`IFM/K2-Horizon-7B` (9.0B dense, 36 layers, 512K context, Apache-2.0, released 2026-09-01) fits at Q5_K_M 6.47 GB or Q6_K 7.39 GB and runs fully on the GPU at 64K. AA components: GPQA-Diamond 75.3%, TB2.1 44.2%, HLE 18.2%, tau3-Banking 27.6%. Vendor: SWE-bench Verified 72.4%, TB2.1 44.6%. It beats every 8-9B model in the catalog (Granite 4.2 8B 5.1, Qwen3.5 9B 5.0) by a wide margin. The 8.9 score is an ESTIMATE: AA has no official v5 index, so I used the catalog's own 5-component linear fit (98 models, RMSE 1.7). `llama.cpp` b11960 supports the `k2-horizon` architecture and the `k2_horizon` tool and reasoning parsers.

### F6 (minor, coverage): Qwen3.6 35B A3B fits 12 GB only on Linux CUDA

The 10.76 GB IQ2_XXS plus KV and overhead is 11.37 GB. Linux CUDA budget is 11.52 GB, Windows is 11.00 GB, unified is 10.00 GB. On Windows the planner falls back to hybrid mode; on a 12 GB Mac the model has no plan. The entry keeps it because it is the only MoE that fits this tier at all and it is the speed pick.

### F7 (minor, catalogue metadata): Qwen3.8 27B has a smaller draft available

`ggml-org/Qwen3.8-27B-GGUF` also publishes `mtp-Qwen3.8-27B-Q4_0.gguf` (1,680,271,776 bytes) next to the Q8_0 draft the catalog uses (3,164,006,816 bytes). For 12-16 GB cards the Q4_0 draft is the difference between GPU and split mode. Swapping it is a catalog-wide decision, so it is an open question rather than a change.

### F8 (minor, evidence): no independent v5 index for several near-miss models

Flint (vendor TB2.1 54.9%, SWE-bench Verified 74.2%), K2 Horizon MoVA 36B A4B (AA components only), Ornith 1.5 9B, SenseNova Loop 9B Preview and Spark X2.6 4B have no official AA v5 index. They are dropped or estimated, not ranked as if they had one.

### F9 (minor, catalog score): Gemma 4 31B's score is now 4.4, not 8.0

`internal/catalog/catalog.json:1024` carries `score: 8.0`, an estimate from legacy components (2026-11-02). Artificial Analysis now publishes an official v5.0 index for Gemma 4 31B (Reasoning) of **4.4** (fetched 2026-11-06), 3.6 points lower. The tier entry uses 4.4. This moves the model below Gemma 4 12B on effective score on a 12 GB Linux card. T01 should decide whether to correct the catalog now or wait for the next snapshot.
