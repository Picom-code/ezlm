# a05. Msty

Desk study, no product installed. All URLs accessed 2026-11-06.

Msty is a closed-source desktop chat app from CloudStack LLC (formerly Mountain Labs). Two
generations matter for this teardown:

- **Msty App v1.x** (the "original" app, still downloadable): a chat front end that bundles a
  renamed Ollama binary as its local engine. This is what most existing write-ups describe.
- **Msty Studio v2.x/3.x** (current, 2025-2026): a rewrite that manages three local engines
  (Ollama, MLX, llama.cpp) and adds a web tier. Msty App v1.x is in maintenance: "We'll continue
  to make it available for the foreseeable future" (https://docs.msty.app/getting-started/onboarding).

The pivot matters for EZLM because Msty moved from "one bundled engine" to "an engine manager",
and from free to a per-seat subscription. Both moves are visible in its issue tracker as churn.

## First-run flow

**v1.x.** First launch shows an onboarding page with three options: *Setup Local AI*, *Add Remote
Models Provider*, *Use Ollama Models (Advanced)* (https://docs.msty.app/getting-started/onboarding).
*Setup Local AI* downloads Gemma 2 (~1.6 GB) by default, with a dropdown to pick another model.
*Add Remote Models Provider* asks for a provider key (OpenAI, Azure, Claude, Gemini, Groq,
OpenRouter, any OpenAI-compatible). *Use Ollama Models* auto-detects an existing Ollama install.
Then the user lands in chats. No hardware scan is described anywhere in this flow, and no model
size is checked against RAM or VRAM before the download starts.

**Studio.** First launch asks intent ("Just exploring / For work / I'm a developer"), then: "Msty
checks your hardware, recommends a compatible local engine and model, and lets you adjust the
recommendation from Light to Powerful before downloading"
(https://docs.msty.ai/studio/getting-started/quick-start). Downloads continue in the background
while the user enters the app. This is the closest thing in the field to EZLM's one-click flow,
and the "Light to Powerful" slider is a nicer affordance than a silent auto-pick.

## Hardware detection

- v1.x: the only documented hardware logic is GPU detection inside the bundled engine. The docs
  ship a support matrix (Nvidia compute 5.0+, AMD on Linux and ROCm 6.1 on Windows, Metal) and
  tell users to check `nvidia-smi -L`, set `CUDA_VISIBLE_DEVICES` / `HIP_VISIBLE_DEVICES`, or
  pass `main_gpu` (https://docs.msty.app/getting-started/gpus-support). That is a user-facing
  troubleshooting matrix, not a detection step in the app.
- Studio: engine choice is hardware-derived. "On Apple Silicon, Msty generally recommends MLX
  when an MLX format is available. Recommendations on other systems depend on the available
  hardware and supported engines" (https://docs.msty.ai/studio/managing-models/local-models).
- There is a manual escape hatch for both: install a local engine from an archive if the default
  installer fails (Studio quick start, same page).

## Model picking

- v1.x: a model selector with pinning, per-model prompt template, label and category
  (Text/Embedding/Vision/Coding) (https://docs.msty.app/features/model-selector). Curated
  "Featured Models" plus a Model Hub over the Ollama registry and Hugging Face GGUF
  (https://docs.msty.app/how-to-guides/download-offline-models). The user does the picking.
- Studio: *Model Matchmaker* ranks models by stated priorities ("Set Priorities, Review Ranked
  Models, Validate in Chat") (https://docs.msty.ai/studio/managing-models/model-matchmaker).
  It ranks by task, not by memory. The hardware fit appears as "hardware-fit information" on the
  Featured catalog and as the engine recommendation above.

## Memory-fit logic

No published memory-fit model. Nothing in either doc set states a RAM/VRAM budget, a KV-cache
estimate, a context-cost model, or an offload plan; the only fit signals are (a) the curated
catalog's size/hardware-fit labels and (b) the engine's own GPU-layer defaults. The user is told
to "use a smaller model to make sure GPU is actually being used" when a GPU is not detected
(https://docs.msty.app/troubleshooting/misc-troubleshooting) — i.e. size selection is the
user's job and the failure mode is silent CPU fallback.

Compare EZLM: `internal/fit/fit.go` computes budgets from scanned hardware (`ComputeBudgets`,
`Plans`, `overhead`/`specOverhead` at internal/fit/fit.go:171-232) and persists `RAMNeed`,
`GPUNeed`, `NGL`, `NCPUMoE` into the serve config
(internal/serve/config.go:44-52). Msty is the "no planner, trust the user" end of the spectrum.

## OpenAI-compatible server and keys

- v1.x: the local engine listens on localhost only by design. A setting *Make Service Available
  on Network* restarts the service bound for the LAN and shows "Service Endpoint > Network IP"
  (https://docs.msty.app/how-to-guides/make-local-ai-service-available-on-the-network). Other
  devices add it as the *Msty Remote* provider. **No API key is mentioned anywhere in that flow.**
  Because the engine is Ollama, the endpoint is Ollama-shaped, so `/v1/chat/completions` works
  for OpenAI clients but there is no key check of Msty's own.
- Studio: per-engine service pages expose "service health, endpoints, versions, logs, start/stop
  controls, and supported acceleration options"
  (https://docs.msty.ai/studio/managing-models/local-models), and the docs list a *Proxy*
  feature for CLI model providers. A separate *Sidecar* + Tailscale path exposes Studio Web to a
  desktop (https://docs.msty.studio/, nav: Sidecar Setup, Tailscale for Sidecar).
- Keys: remote provider keys are stored in the OS keychain by default, with an opt-out to store
  them unencrypted in the workspace folder; importing a workspace on a second device yields
  "Error while decrypting the ciphertext" unless keys are re-entered
  (https://docs.msty.app/troubleshooting/misc-troubleshooting).
- EZLM contrast: `internal/keys.New()` mints `ezlm-` + 40 base62 chars, and `serve.Config` has
  `Keys []APIKey`, `LAN bool`, `Port int` (internal/keys/keys.go:12, internal/serve/config.go:36-38).
  EZLM is already ahead on server auth; Msty is ahead on making the endpoint findable.

## Coding-agent integrations

Weak and mostly indirect. v1.x has no MCP support; Msty Studio adds "MCP support"
(https://docs.msty.app/getting-started/onboarding comparison table). Studio's *Vibe CLI Proxy*
"connects command-line model providers" (https://docs.msty.ai/studio/managing-models/model-matchmaker
nav). The usual pattern is a user pointing Continue/Cline/Zed at the Ollama port manually; Msty
does not write config for the agent, unlike EZLM's OpenCode/Hermes wiring in `internal/integrate`.
Msty Studio also documents "Use Studio Docs with AI Tools", which is docs-only.

## Update mechanism

- App: "Msty updates itself automatically in the background"
  (https://docs.msty.app/getting-started/changelog). There is a dedicated failure page: stop the
  Local AI service, kill all `msty` processes and `ollama-runner`, Check for Updates, restart;
  if it persists, reinstall
  (https://docs.msty.app/troubleshooting/stuck-at-app-update).
- Engine: bundled and therefore stale by construction. v1.9 (April 28, 2025) shipped "Local AI
  version 0.6.6" (changelog). Users who want a newer engine follow manual per-OS steps that end
  in renaming `ollama` to `msty-local` and dropping `lib/` into the app data directory; the doc
  even asks users to upvote an Ollama PR because the official Windows build opens a blank
  Terminal window during chat
  (https://docs.msty.app/how-to-guides/get-the-latest-version-of-local-ai-service).
- This is the single clearest update failure mode in the field: app cadence and engine cadence
  are coupled, and the only supported remedy for drift is hand-copying binaries.

## Windows on Arm, AMD and Intel GPUs

- **Windows on Arm:** effectively unsupported in v1.x. The maintainer: "We kind of have an ARM
  version running locally. Unfortunately, there are a few dependencies that don't support ARM
  esp. LanceDB that we use for KnowledgeStack... it's more work than the demand is there for Arm
  Windows" (https://github.com/cloudstack-llc/msty-docs/issues/15). The issue was closed because
  the repo is docs-only, not because it was fixed. No arm64 Windows installer is documented. For
  Studio this is unverified; the engine manager could in principle use llama.cpp, but no doc
  states Arm support.
- **AMD on Windows:** supported "out of the box" with a dedicated ROCm installer, but the docs
  spend a full page on failure modes: try the generic installer, then CPU-only, verify with
  `./msty-local.exe serve`, and as a last resort drop in a community Ollama build
  (`likelovewant/ollama-for-amd`) plus hand-picked ROCBLAS libraries
  (https://docs.msty.app/troubleshooting/amd-rocm-windows-issues). That is a support burden EZLM
  should expect to inherit, not a solved problem.
- **AMD on Linux:** supported cards listed, plus `HSA_OVERRIDE_GFX_VERSION` spoofing for
  unsupported ones and a SELinux `container_use_devices` note
  (https://docs.msty.app/getting-started/gpus-support).
- **Intel:** no Intel Arc or Vulkan entry in the GPU matrix at all; only Nvidia, AMD and Metal
  (same page). EZLM should not assume Msty is a reference for Arc.

## Recommendations for EZLM

**1. Show the chosen endpoint and a one-toggle LAN share, with the key in the same sentence.**
Evidence: Msty's network page is five steps and a firewall caveat, and its endpoint IP moves with
Wi-Fi (https://docs.msty.app/how-to-guides/make-local-ai-service-available-on-the-network,
https://github.com/cloudstack-llc/msty-docs/issues/45). EZLM already has `LAN` and named keys in
`internal/serve/config.go:36-38`; what is missing is a single "copy this URL and key" surface and
a warning that DHCP changes the IP. Effort **S**. Priority **P1**.

**2. Explain the pick and offer one lighter and one heavier alternative.**
Evidence: Studio's first run checks hardware, recommends an engine and model, and lets the user
slide "Light to Powerful" before downloading
(https://docs.msty.ai/studio/getting-started/quick-start); v1.x has no such step at all. EZLM
already computes the alternatives in `internal/fit` (`Plans`, internal/fit/fit.go:232); exposing
the runner-up plans as a plain-language "why this model" line plus two alternatives turns an
opaque auto-pick into a defensible one. Effort **M**. Priority **P1**.

**3. Import an existing Ollama model store and local GGUF files before downloading anything.**
Evidence: Msty's "Use existing Ollama Models" is a models-path setting and a service restart, and
Studio imports GGUF and Safetensors directories
(https://docs.msty.app/how-to-guides/use-existing-ollama-models,
https://docs.msty.ai/studio/managing-models/local-models). EZLM's value is the first run; a
user with 40 GB of models already on disk should not re-download them. Effort **M**. Priority **P2**.

**4. Decouple engine updates from app updates, and keep the previous engine for rollback.**
Evidence: Msty v1.9 shipped Ollama 0.6.6 in April 2025 and the only path to a newer engine is
copying binaries by hand; a .deb update broke installs; a dedicated page exists for stuck app
updates (https://docs.msty.app/getting-started/changelog,
https://docs.msty.app/how-to-guides/get-the-latest-version-of-local-ai-service,
https://github.com/cloudstack-llc/msty-docs/issues/19). EZLM has `internal/update` and a tagged
engine (`EngineTag` in `internal/serve/config.go:54`); pin the engine tag per deploy, show it in
the report, and keep the prior engine directory so a bad build is one command to undo. Effort
**M**. Priority **P1**.

**5. Prove the GPU is actually being used, and say so when it is not.**
Evidence: Msty's own remedy for "my GPU is not being used" is "use a smaller model to make sure
GPU is actually being used", after checking Task Manager by hand
(https://docs.msty.app/troubleshooting/misc-troubleshooting); AMD on Windows has a whole
escalation ladder (https://docs.msty.app/troubleshooting/amd-rocm-windows-issues). EZLM already
has `CPUFallback` in `internal/serve/config.go:55-57` and a report package; run a two-token
generation after deploy and report backend, layer count and the reason for any fallback, so the
user never has to open Task Manager. Effort **M**. Priority **P2**. This also covers Windows on
Arm, where Msty's answer is "not supported" (issue 15).

- Is there an auth token on the v1.x LAN endpoint? The docs never mention one; the engine is
  Ollama, which has none by default. Unverified.
