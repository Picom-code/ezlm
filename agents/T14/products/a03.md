# Jan (a03)

Desk study of Jan, the desktop app from Menlo Research (`janhq/jan`, Apache 2.0). All URLs
accessed 2026-11-06. Version studied: 0.8.8, released 2026-10-28
(https://github.com/janhq/jan/releases/tag/v0.8.8).

Jan is the closest thing to a competitor for EZLM's *shape*: a desktop app that installs an
engine, downloads a model, and exposes an OpenAI-compatible URL. It is not close in ambition:
Jan is a chat app with a server attached, EZLM is a deployer that hands the user a URL and a key.

## First-run flow

- Installer, then a guided wizard since v0.8.5: welcome, engine setup, first model, consent page.
  Before that the app opened straight into chat with no engine and no model. Source: v0.8.5 release
  notes, https://github.com/janhq/jan/releases/tag/v0.8.5.
- The docs still say "Jan automatically downloads its default foundation model on first launch"
  (https://docs.jan.ai/desktop/quickstart). That is stale relative to the wizard in the 0.8.5 notes;
  treat the release notes as authoritative.
- The bundled engine is installed with the app, not downloaded per machine. v0.8.5 removed the
  per-machine backend download and the engine auto-update setting entirely. Same source.
- The default model is a Jan-branded one (Jan-Code-4B, Jan-v3-4B, Jan-v2-VL are listed in the
  quickstart), so the first-run path is first-party, not "pick from a catalogue".
- Cost of the install is large: the 0.8.8 x64 Windows installer is 572 MB, the Linux .deb 1.06 GB,
  the universal macOS dmg 116 MB (release asset sizes from the GitHub releases API, 2026-11-06).

## Hardware detection

- Settings > Hardware > GPUs lists GPUs with on/off switches, and a card can offer a backend choice
  when more than one is available (CUDA and Vulkan). Source:
  https://docs.jan.ai/desktop/local-engine/llama-cpp.
- Detection is not a separate probe with a fallback story. It is whatever the bundled llama.cpp
  build reports. When that build's libraries do not resolve, Jan reports "No devices found" with a
  working `nvidia-smi`: issue #8145, hardcoded CI RUNPATH and an unbundled `libnccl` in the Linux
  CUDA backend, https://github.com/janhq/jan/issues/8145 (6 reactions, opened 2026-05-16, still open).
- v0.8.7 added driver-version logging at engine start and a message telling the user to update the
  driver when it is too old for the engine (release notes, https://github.com/janhq/jan/releases/tag/v0.8.7).
- Documented minimums: 8 GB RAM, 6 GB VRAM for any GPU, x64 with AVX2 or ARM64
  (https://docs.jan.ai/desktop/install/windows).

## Model picking

- The Hub shows a fit pill per model: **Fits**, **May be slow**, **Won't fit**. Quantisations are
  grouped Small / Balanced / Large, and one carries a **Recommended** tag. The docs are explicit
  that "no data is downloaded to determine fit status" (https://docs.jan.ai/desktop/manage-models).
  So the pill is a local estimate from the model metadata, not a benchmark.
- There is no "smartest model that fits" ranking and no explanation of why one model is recommended
  over another. The user still chooses.
- Import paths: Hub download, Hugging Face model ID search, "Use this model" button on HF, and
  linking a local GGUF file in place (manage-models doc; llama-cpp doc).
- v0.8.5 migration removed the `n_gpu_layers: 100` an earlier version had written into model.yml,
  so GPU offload is decided automatically again (v0.8.5 notes). That is a useful admission: Jan's
  own tuning had been over-offloading and the fix was to stop pinning it.

## Memory-fit logic

- Fit is advisory and per-model, not a planner. The engine settings expose the raw llama.cpp knobs:
  context size, GPU layers, batch size, KV cache K/V type, disable KV offload, mlock, mmap, flash
  attention, `--n-cpu-moe` is not surfaced as a first-class concept the way EZLM does it.
  Source: https://docs.jan.ai/desktop/local-engine/llama-cpp.
- Engine-wide defaults live in `router.preset.ini` and per-model entries override them. A router
  loads and unloads models on demand since v0.8.0, with **Max Concurrent Models** as the control.
  Same source.
- Two defaults matter for memory safety: Parallel Sequences is 0 (auto) since v0.8.5, and v0.8.6
  made MTP models use one slot when auto is set, after 4 reserved slots pushed a 12 GB card into
  shared memory (https://github.com/janhq/jan/releases/tag/v0.8.6). The failure mode was real and
  shipped.
- Prompt cache defaults to 8 GiB on disk (`--cache-ram` 8192 MiB), and "Remember Conversations
  Between Sessions" is on by default since v0.8.5, capped by a Conversation Cache Disk Limit.
  This is memory *and* disk pressure EZLM does not have to model.
- There is no hard safety margin in Jan's model. Nothing in the docs says the OS is protected from
  a model that just fits; the user can set any context and any GPU layer count.

## OpenAI-compatible server and keys

- Base URL `http://127.0.0.1:1337/v1`, port 1337, prefix `/v1`, all configurable
  (https://docs.jan.ai/desktop/api-server).
- API key is **optional and empty by default**. "Leave the field empty to disable authentication
  (not recommended when binding to 0.0.0.0)." The key is any string the user types; there is no
  generated format. Same source.
- Binding: `127.0.0.1` default, `0.0.0.0` for LAN. Trusted Hosts is a comma-separated hostname
  allowlist added in v0.8.8, and CORS is on by default (it was a no-op switch before v0.8.8).
  Same source plus v0.8.8 notes.
- The server needs a local model to start; it can route to remote providers afterwards, but a
  remote provider does not satisfy the startup requirement. That is a strange coupling: the URL
  exists only if a local model is loadable (api-server doc).
- Port 1337 does not fall back. "If that port is taken ... the server fails to bind"
  (https://docs.jan.ai/desktop/troubleshooting). The user is told to find and free the port.
- Server-side tool execution is opt-in per request path, and requests run MCP tools only when
  Settings > Local API Server allows it (v0.8.8 notes).
- Security history is directly relevant: GHSA-x6p8-7cp8-c3p6, binding to 0.0.0.0 accepted any
  Host header before v0.8.5, fixed by the Trusted Hosts check (v0.8.5 and v0.8.8 notes).

## Coding-agent integrations

- Claude Code is a first-class integration: Jan writes the shell profile, keeps its lines in one
  marked block, and refuses variables that change how programs are found (PATH, PATHEXT, SystemRoot,
  ComSpec, LD_*, DYLD_*, JAN_*, GPU runtime paths) (v0.8.8 notes). That refusal list is a good
  model for any installer that edits a profile.
- A `jan` CLI exists as a separate install since v0.8.5 (it was bundled and on PATH before). The
  desktop app no longer manages it, so on macOS and Linux an old CLI is left in place at v0.8.4 and
  on Windows the updater removed it, which is a stale-binary trap (v0.8.5 notes).
- MCP servers, built-in web search and fetch, and subagents (explore, research, review, debug) are
  in-app agent features, not a coding-agent surface (v0.8.7 notes).
- For external agents the only contract is the OpenAI-compatible URL, which is the same contract
  EZLM offers. Jan's advantage is that the key can be empty; EZLM's is that the key is always set.

## Update mechanism

- In-app updater, signed artifacts, update channel embedded in the app; `latest.json` is published
  per release (release assets, 2026-11-06).
- Engine updates with the app since v0.8.5, so there is one version to reason about, at the cost of
  a 0.5 to 1 GB download for an engine bump.
- Failure handling is poor: a failed in-app update closes the dialog and reports nothing; the reason
  is only in the log, with no retry until the next check. Issue #9137,
  https://github.com/janhq/jan/issues/9137, filed during 0.8.5 QA, still open and listed under
  "Known issues" in v0.8.8.
- Update cleanup was also buggy: v0.8.5 had to stop the running engine, MCP servers and agent
  shells before the installer ran, and had to stop an engine 0.8.4 left running at next start.

## Windows on Arm and AMD/Intel GPUs

- Windows on Arm: an ARM64 installer exists (`Jan_0.8.8_arm64-setup.exe`, 647 downloads against
  28,833 for x64 on the same release), and the docs say ARM64 CPUs are supported, but every GPU
  vendor named is x86 (NVIDIA, AMD, Intel Arc). Nothing in the docs says whether Adreno or any WoA
  GPU is used, so the honest reading is CPU-only on WoA until proven otherwise. Sources: release
  assets, https://github.com/janhq/jan/releases/tag/v0.8.8; https://docs.jan.ai/desktop/install/windows.
- Linux on Arm64 has no installer; the README links to a community how-to in issue #4543
  (https://github.com/janhq/jan/issues/4543), which is a support burden, not a build.
- AMD: bundled Vulkan only. HIP/ROCm requires running your own `llama-server` and adding it as a
  custom endpoint, and "this does not replace Jan's bundled engine" (Windows install doc). The old
  backend selector is gone.
- Intel Arc: Vulkan required, same doc.
- Intel Macs: local models stopped working in v0.8.0 and the bundled engine is Apple Silicon only;
  v0.8.5 still runs remote providers on an Intel Mac (v0.8.5 notes). That is a clean example of
  dropping a platform without dropping the app.

## Three to five recommendations for EZLM

### R1. Add a Host allowlist to the LAN server, not just a key (priority P1, effort S)

Jan shipped the same hole EZLM has: binding to `0.0.0.0` accepted any Host header, so a web page
could reach the local API by DNS rebinding. Jan fixed it with Trusted Hosts (v0.8.5, GHSA-x6p8-7cp8-c3p6,
https://github.com/janhq/jan/releases/tag/v0.8.5). EZLM's `Config` has a `LAN bool` and a host
string, and passes `--api-key` to llama-server (`internal/serve/config.go`), so the key protects
against a blind caller but not against a browser that can guess or be given the key. Accept only
loopback, private LAN IPs and configured names when LAN is on; reject anything else with 403.
Evidence: Jan's CVE-class fix and its 0.8.8 notes. Small change, real security value.

### R2. Show the fit pill and the expected speed before the download (priority P1, effort M)

Jan's Hub shows Fits / May be slow / Won't fit and a Recommended quant, computed locally with no
network call (https://docs.jan.ai/desktop/manage-models). EZLM already has the better engine
(`internal/fit` tries quant × context × KV × placement and ranks by effective intelligence), but
the user meets it after the decision, in the deploy. Surface the same three states, plus tok/s, in
the model choice, and say which quant is recommended and why. This is EZLM's strongest asset
against Jan: Jan guesses fit, EZLM computes it.

### R3. Keep the API key mandatory and make that visible (priority P2, effort S)

Jan's key is optional and empty by default, so the common local install has an unauthenticated
OpenAI endpoint on 1337 (https://docs.jan.ai/desktop/api-server). EZLM generates `ezlm-` + 40
base62 characters and always passes `--api-key` (`internal/keys/keys.go`,
`internal/serve/config.go`). Keep that, and put the key and URL in front of the user on the success
screen with a copy button, so "no key" never becomes a support question. Also print the key in the
`ezlm status` output.

### R4. Make a failed update say why, and offer retry (priority P2, effort S)

Jan's silent update failure is a known, still-open bug: the dialog closes, the reason is only in
the log, no retry until the next check (https://github.com/janhq/jan/issues/9137). EZLM downloads
from the GitHub releases API (`internal/update/update.go`) and can fail on a rate limit, a digest
mismatch or a proxy. Show the reason in the update UI, keep the current version running, and add a
retry button. A user who cannot tell "already latest" from "download failed" will reinstall by hand.

### R5. Put engine build and driver version in the support report (priority P3, effort S)

Jan learned this the hard way: v0.8.7 started logging the NVIDIA driver version and telling the
user to update a too-old driver, and the llama.cpp page shows version, build and commit
(https://github.com/janhq/jan/releases/tag/v0.8.7). EZLM stores `EngineTag` in its config
(`internal/serve/config.go`); also record the llama-server build string and the GPU driver version
at deploy time, and include both in the report the user can copy. It turns "it does not work" into
a fixable ticket, and it costs almost nothing.
