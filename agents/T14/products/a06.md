# AnythingLLM (a06)

Desk study, no install. Everything below is from public docs, the public repo and its issue tracker, read on 2026-11-06. AnythingLLM is not a model deployer like EZLM: it is a RAG and agents workspace that can *use* a local model, and since v1.19 it can also ship one. That difference is the useful part of this teardown.

Version in scope: v1.19.0, released 2026-10-26 ([release](https://github.com/Mintplex-Labs/anything-llm/releases/tag/v1.19.0)). Repo: 68,006 stars, 343 open issues, MIT ([repo](https://api.github.com/repos/Mintplex-Labs/anything-llm), accessed 2026-11-06).

## 1. First-run flow

Desktop is a one-click Electron app for macOS, Windows and Linux; Docker is the multi-user path ([desktop overview](https://docs.anythingllm.com/installation-desktop/overview), accessed 2026-11-06). Onboarding asks for the LLM provider, the embedder and the vector database, then the app opens a workspace. With the built-in provider selected, the model download starts from the onboarding screen and its progress is shown top-right of the window ([built-in LLM](https://docs.anythingllm.com/setup/llm-configuration/local/built-in), accessed 2026-11-06).

So the first run is a provider picker, not a machine-aware setup. Nothing on the documented onboarding path scans the GPU and says "this model fits". That is the core difference from EZLM, whose first run is scan, pick, install, hand over a URL and key (`BETA.md:21-24`).

## 2. Hardware detection

AnythingLLM itself does not appear to detect hardware; it delegates to the engine. The built-in provider is Lemonade, AMD's open-source local server, running llama.cpp on Vulkan (AMD, Intel, NVIDIA), CUDA (NVIDIA, picked automatically when the driver supports it) or Metal (Apple Silicon), and on AMD Ryzen AI XDNA2 NPUs through FastFlowLM ([built-in LLM](https://docs.anythingllm.com/setup/llm-configuration/local/built-in), accessed 2026-11-06).

On Docker the user does the detection: `--gpus all` for NVIDIA, `--device /dev/dri` for AMD and Intel, and Docker on macOS cannot use the Apple GPU at all. The built-in engine is opt-in there (`ENABLE_BUILT_IN_LLM=true`) and only on the `latest` image from v1.18.0 on. That is a reasonable split (desktop auto, server explicit), and it is a useful precedent for EZLM's "report what the engine line says" approach.

## 3. Model picking

The built-in provider shows a model table with a ⚡ marker on faster multi-token-prediction models, and during onboarding it recommends three models for the machine's GPU or memory. The user picks. Beyond the table, the user can pull any GGUF from Hugging Face as `owner/repo` or `owner/repo:QUANT`, or import a local `.gguf`, and can change model later in Settings ([built-in LLM](https://docs.anythingllm.com/setup/llm-configuration/local/built-in), accessed 2026-11-06).

That is a catalogue with a shortlist, not a planner. There is no documented step that ranks models by quality-per-token or predicts tokens per second. EZLM's `internal/fit` does exactly that: it tries every quant × context × KV-cache type × placement and ranks by quantisation-adjusted intelligence subject to a speed floor (`internal/fit/fit.go:1-20`). EZLM is clearly ahead here; the AnythingLLM lesson is presentation, not logic: show the shortlist and the numbers, let the user override.

## 4. Memory-fit logic

No documented pre-download fit check. The system requirements page gives guidance (16 GB RAM, 8-core CPU; 8-12 GB+ VRAM "great" on Windows; any M-series Mac) and says the LLM is the bottleneck, not AnythingLLM ([system requirements](https://docs.anythingllm.com/installation-desktop/system-requirements), accessed 2026-11-06). Fit at load time is left to llama.cpp/Lemonade, which will fail or offload to CPU. On Docker the docs claim "RAM and GPU memory freed automatically when you switch the system LLM to another provider", which is a lifecycle behaviour EZLM also needs (it stops llama-server).

Consequence: a user can download a 20 GB model on a 16 GB laptop and only find out at load. I could not find a doc promising a warning, so this is inference from the absence of a documented check, not a confirmed bug. Marked as such in the report.

## 5. OpenAI-compatible server and keys

There is a full developer API under `/api/v1`, documented live at `/api/docs` on the instance, with API keys created per account in the UI ([API access](https://docs.anythingllm.com/features/api), accessed 2026-11-06). Auth is `Authorization: Bearer <key>` checked against the `api_keys` table (`server/utils/middleware/validApiKey.js`). Keys are not scoped per workspace in the endpoint I read; anyone with a key can use the API, which the docs say explicitly.

The OpenAI-compatible surface is deliberately narrow:

- `GET /api/v1/openai/models` lists **workspaces**, not models: `id` is the workspace slug and `owned_by` is the chat provider (`server/endpoints/api/openai/index.js`).
- `POST /api/v1/openai/chat/completions` takes `model` = workspace slug, `messages`, `temperature`, `stream`; the last message must be `role: "user"`.
- The `tools` parameter was **not** supported; it was requested in [#3753](https://github.com/Mintplex-Labs/anything-llm/issues/3753) (18 reactions, closed 2025-05-02) and the endpoint still routes through AnythingLLM's own chat pipeline rather than a raw model.

That last point is the big one for coding agents. A coding agent that sends `tools` or expects `model` to be a model name will not work against AnythingLLM without an adapter, and every request runs the workspace RAG pipeline, so prompts are rewritten and documents are injected. EZLM's server is llama-server's own `/v1` with `--alias` set to the model id and `--api-key` holding an `ezlm-` key (`internal/serve/config.go:99-100`, `internal/serve/config.go:115-131`, `internal/keys/keys.go:12-24`), so tools and `/v1/models` behave like a normal OpenAI endpoint. Keep it that way and test it.

## 6. Coding-agent integrations

Nothing in the docs targets coding agents. Integrations are MCP **inbound** (AnythingLLM's agent can call MCP tools; you edit `anythingllm_mcp_servers.json` and manage servers in the UI) ([MCP overview](https://docs.anythingllm.com/mcp-compatibility/overview), accessed 2026-11-06), agent skills, a browser extension, and "Model Router" for switching providers. There is no "Open in Cursor/Claude Code/OpenCode" flow and no per-editor setup doc. Contrast EZLM, whose beta explicitly starts OpenCode and Hermes with the URL and key already set (`BETA.md:24`). This is a place EZLM should keep investing; it is a differentiator, not a commodity.

## 7. Update mechanism

Manual. The docs say download the new `.dmg`/`.exe`/`.AppImage` and reinstall over the old one, or `brew upgrade --cask anythingllm` on macOS; data is preserved ([update](https://docs.anythingllm.com/installation-desktop/update), accessed 2026-11-06). There is no documented in-app auto-updater, and the Linux AppImage path has a long-standing update failure report ([#1077](https://github.com/Mintplex-Labs/anything-llm/issues/1077), 18 comments, closed 2024-04).

The nastier failure mode is the engine migration: v1.19 moved the built-in engine from Ollama to Lemonade, and the docs warn that switching "deletes the old engine and the models that were downloaded with it", so every model must be re-downloaded ([built-in LLM](https://docs.anythingllm.com/setup/llm-configuration/local/built-in), accessed 2026-11-06). For a 20-60 GB download that is a real cost. EZLM's update keeps the model running and the models on disk (`BETA.md:36-38`), which is the right behaviour; the lesson is to make engine swaps additive and reversible.

## 9. Windows on Arm, AMD and Intel GPUs

- **Windows on Arm**: a dedicated Qualcomm QNN provider exists in the desktop app, and the two most-commented issues in the tracker are about it not working ([#2962](https://github.com/Mintplex-Labs/anything-llm/issues/2962), [#3194](https://github.com/Mintplex-Labs/anything-llm/issues/3194)). The realistic WoA path is CPU, with NPU as an experiment.
- **AMD**: Vulkan through Lemonade is the documented desktop path; Ryzen AI XDNA2 NPUs get FastFlowLM; Docker needs `--device /dev/dri`.
- **Intel**: Vulkan, same as AMD; Arc is not called out separately anywhere in the built-in docs.
- **Docker on macOS**: no Apple GPU, CPU only, stated plainly.

## Recommendations for EZLM

**R1. Show the shortlist, not just the verdict (M, P1).** AnythingLLM's built-in provider puts three recommended models and a full table in front of the user, with size and a speed marker, and lets them pull any GGUF ([built-in LLM](https://docs.anythingllm.com/setup/llm-configuration/local/built-in), accessed 2026-11-06). EZLM already computes the better answer in `internal/fit` but presents one pick. Add a "why this model" panel with the two runner-up plans and their predicted tok/s and memory, and an override that re-runs fit for a chosen model. Evidence: AnythingLLM's table is the feature users actually use; EZLM's planner is invisible.

**R2. Publish and test an OpenAI conformance page (S, P1).** AnythingLLM's compatible endpoint lists workspaces as models and dropped `tools` until 2025, which is exactly the kind of surprise that breaks coding agents ([#3753](https://github.com/Mintplex-Labs/anything-llm/issues/3753), 18 reactions). EZLM serves llama-server directly, so it should already pass: add a small `httptest` conformance suite (`/v1/models` returns the `--alias`, `tools` round-trips, `stream: true` works, bad key gets 401) and a docs page that names the base URL `http://127.0.0.1:<port>/v1` and the `ezlm-` key format. Cheap insurance for the beta's main promise.

**R3. Make engine swaps additive (M, P2).** AnythingLLM's move to Lemonade deletes the old engine and all downloaded models and forces a re-download ([built-in LLM](https://docs.anythingllm.com/setup/llm-configuration/local/built-in), accessed 2026-11-06). When EZLM next changes engine or backend, download the new engine beside the old one, switch only after a successful load, and keep the models directory untouched. Show the extra disk cost before the download starts.

**R4. Treat the NPU as a beta label, not a feature (S, P1).** The two most-commented issues in a 68k-star project are both "the Snapdragon NPU does not work" ([#2962](https://github.com/Mintplex-Labs/anything-llm/issues/2962), 69 comments; [#3194](https://github.com/Mintplex-Labs/anything-llm/issues/3194), 26). EZLM's beta text promises ARM laptops will work. On WoA, ship CPU/Vulkan as the supported path, keep any NPU path behind a flag, and make the System page state which one is actually in use so a report is diagnostic rather than a conversation.

**R5. Keep the storage-location choice and add migration (M, P3).** One of AnythingLLM's most-reacted open feature requests is choosing the storage folder on a multi-drive Windows machine (24 reactions, [#3087](https://github.com/Mintplex-Labs/anything-llm/issues/3087)). EZLM already lets the user pick the models drive (`BETA.md:23`), so it is ahead; the gap is moving an existing install. Add "move models to another drive" that copies, verifies and only then switches the path.
