# a07. llamafile (Mozilla.ai)

Desk study. All URLs accessed 2026-11-06. Version in scope: llamafile 0.10.6
(released 2026-09-15, <https://github.com/mozilla-ai/llamafile/releases>), the
0.10 build line that replaced the 0.9 "classic" builds.

llamafile is the opposite design point from EZLM: one self-contained executable
per model, no installer, no daemon, no model manager, no planner. It is a
portable llama.cpp distribution, not a deployment product. That makes it a good
source of ideas about portability, server compatibility and honest fallbacks, and
a poor source of ideas about first-run guidance and hardware fit.

## 1. First-run flow

There is no installer and no first-run wizard. The documented flow is:

1. Download a pre-built model-bundled llamafile, e.g. `Qwen3.5-0.8B-Q8_0.llamafile`
   (1.77 GB).
2. `chmod +x` it on macOS/Linux/BSD (one time).
3. Run it. On Windows, rename the file to add `.exe`.
4. A chat TUI opens in the terminal and, in the default "combined mode", an HTTP
   server also starts at `http://localhost:8080` with llama.cpp's Web UI.
5. `Ctrl-C` to stop.

Sources: <https://docs.mozilla.ai/llamafile/getting-started/quickstart>,
<https://docs.mozilla.ai/llamafile/using-llamafile/running_llamafile> ("Combined
mode is the default for the last generation of llamafiles").

Friction that the docs themselves admit:

- macOS: the first run needs Xcode Command Line Tools to build a Metal module;
  unsigned binaries hit Gatekeeper ("cannot be opened because the developer
  cannot be verified") and need a Privacy & Security allow.
- Linux: `binfmt_misc`/`run-detectors`/WINE can mis-handle the APE format; the
  fix is a manual `/proc/sys/fs/binfmt_misc/register` write.
- WSL: a systemd unit and disabling WIN32 interop are documented workarounds.
- Any platform: if the process is killed instantly, the docs blame CrowdStrike
  and tell the user to ask for a whitelist.

Sources: <https://docs.mozilla.ai/llamafile/reference/troubleshooting>.

Assessment: a technically literate user gets to a chat in two commands, which is
excellent. A non-technical user has no idea which file to download (the release
page ships `llamafile`, `llamafile-thin`, `whisperfile`, `transcribefile`,
`diffusionfile`, `zipalign`, plus a zip) and no guidance about what will fit.
EZLM's one-click flow is strictly better for the target user; llamafile's
zero-install, zero-daemon property is the thing worth borrowing for recovery.

## 2. Hardware detection

There is essentially none at the product level. The docs describe the detection
that llama.cpp/ggml performs at load time:

- CPU: AMD64 requires AVX or the binary refuses to run; AVX2/AVX512/FMA/F16C/
  VNNI are enabled at runtime. ARM64 requires ARMv8a+.
- GPU backends are loaded dynamically: `ggml-(cuda|rocm|vulkan).(so|dll)` is
  looked for next to the executable, then in the bundle, then in
  `~/.llamafile/v/LLAMAFILE_VERSION`, then in `$HOME`.
- If a library loads but reports no usable device, llamafile skips it and tries
  the next backend; if nothing works it silently falls back to CPU.
- `--gpu auto|nvidia|amd|apple|vulkan|disable` forces a backend; forcing one is
  the documented way to turn a quiet CPU fallback into a startup error.

Source: <https://docs.mozilla.ai/llamafile/reference/support>.

So "detection" is backend probing, not capacity planning. Nothing reads total
RAM, free VRAM, or the model's layer count to choose a configuration. The user
is expected to know that NVIDIA/AMD owners must pass `-ngl 999`, and that Metal
offloads by default.

## 3. Model picking

Manual and curated. The pre-built list has 13 model files from 1.6 GB to 19 GB,
each a fixed model+quantization, and the only stated heuristic is "the smaller
the file, the more easily it will run". The quickstart picks the 0.8B because it
is "the smallest one we have built a llamafile for".

Sources: <https://docs.mozilla.ai/llamafile/getting-started/pre-built-llamafiles>,
quickstart page above.

For external weights the user passes `-m model.gguf` or lets llamafile download
one with `-hf`/`--hf-repo`/`--model-url` at startup (flags listed in
<https://docs.mozilla.ai/llamafile/reference/cli_arguments>). There is no
recommendation engine, no "smartest model that fits", no quality/speed tradeoff.
The user picks the file; the file is the deployment.

Consequence: the product cannot answer "what should I run on this laptop", which
is exactly the question EZLM's catalog plus `internal/fit` answers. It also means
llamafile never recommends a model too large for the machine; the user discovers
that at load time, via OOM or swap death (see complaints).

## 4. Memory-fit logic

No planner. Fit is delegated to llama.cpp:

- Weights are memory-mapped by default (`-lm auto`; alternatives `none`, `mmap`,
  `mlock`, `mmap+mlock`, `dio`), so load does not require a full copy in RAM,
  but inference pages the whole model in.
- GPU placement is a single number: `-ngl N` (`999` = all layers), with
  `-sm/--split-mode`, `-ts/--tensor-split`, `-mg/--main-gpu`, and
  `-ncmoe/--n-cpu-moe` for MoE experts.
- llamafile inherits llama.cpp's automatic fitting flags `--fit`,
  `--fit-target`, `--fit-ctx`. They are listed in the CLI reference but are not
  explained or recommended anywhere in llamafile's docs, and are opt-in.
- Context is manual: `-c/--ctx-size`, and `0` means the model default. The
  running-a-llamafile page tells agent users to "choose a context size which is
  large enough (but still fits your memory)", with no way to compute it.

Sources: <https://docs.mozilla.ai/llamafile/reference/cli_arguments>,
running-a-llamafile page above.

There is no headroom model, no OS reserve, no KV-cache sizing, no quant choice
per machine. On Windows there is an extra hard constraint the docs call out
twice: executables over 4 GB do not run, so any model above ~4 GB must be a
separate GGUF plus the `llamafile` binary.

Contrast with EZLM: `internal/fit/fit.go` enumerates quant × context × KV type ×
placement (GPU, hybrid `--n-cpu-moe`, split `-ngl`, CPU), computes GPU/RAM
budgets with margins and an OS floor, ranks by effective intelligence subject to
a tok/s floor, and emits `Args()`. llamafile is one flag and hope.

## 5. The OpenAI-compatible server and keys

Server mode (`--server`, or combined mode by default) exposes llama.cpp's HTTP
API:

- Base URL `http://127.0.0.1:8080`; `--host`/`--port` change it;
  `--api-prefix` mounts everything under a path.
- OpenAI-compatible: `/v1/chat/completions`, `/v1/responses` (no
  `previous_response_id`), `/v1/completions`, `/v1/embeddings`, `/v1/rerank`,
  `/v1/audio/transcriptions`, `/v1/models`, token-count endpoints.
- Anthropic-compatible: `POST /v1/messages` and `/v1/messages/count_tokens`,
  including `system`, `stop_sequences`, streaming and Anthropic-shaped tools.
- llama.cpp native: `/health`, `/props`, `/slots`, `/tokenize`, `/infill`,
  `/metrics`, `/tools`.
- The `model` field is required even with one model loaded; clients use a
  placeholder like `local-model`; `--alias` sets a stable name.

Authentication: `--api-key` or `--api-key-file`, checked against either
`Authorization: Bearer` or `X-Api-Key` (the latter deliberately matches
Anthropic's `x-api-key`). With no key configured, no header is needed. The docs
warn to keep the default localhost binding and to set a key before exposing the
server; they also say CORS "should not be used instead of authentication".

Source: <https://docs.mozilla.ai/llamafile/using-llamafile/api>.

Assessment: this is the strongest part of llamafile and the part EZLM should
copy. One key, one process, both API dialects, Anthropic header compatibility.
EZLM today issues named keys (`internal/keys/keys.go`, `internal/serve/config.go`
`Keys []APIKey`) and verifies its own server by calling `/v1/models` with a
Bearer key (`internal/serve/client.go`), but has no Anthropic `/v1/messages`
surface.

## 6. Coding-agent integrations

No first-party editor extensions. The integration story is "point any
OpenAI/Anthropic client at the base URL":

- `export OPENAI_BASE_URL=http://127.0.0.1:8080/v1` and
  `OPENAI_API_KEY=no-key-required`, then the official `openai` Python SDK works
  unchanged (quickstart).
- For agent frameworks the docs say to add `--jinja` and a context size large
  enough for the agent's prompts, and to use `--tools` if the client will call
  llama.cpp's built-in tools through `POST /tools`.
- `agentfile` is a bundled single-file agent runner: tools off by default,
  `read_only`/`all`/explicit list, confirmation prompts for write/exec/fetch,
  `--session` JSONL transcripts, `--trace` OTLP, exit code 4 on iteration cap.
- There is one old request for VS Code integration (issue #167, 4 reactions,
  closed) and none of the major editors document llamafile as a supported
  backend.

Sources: <https://docs.mozilla.ai/llamafile/using-llamafile/agentfile>,
running-a-llamafile page, <https://github.com/mozilla-ai/llamafile/issues/167>.

Assessment: broad compatibility by construction, no guided setup. EZLM's
`internal/integrate` (writing per-tool config for Claude Code, Codex, OpenCode,
etc.) is a real differentiator; the missing Anthropic endpoint is the gap that
would block Anthropic-native agents.

## 7. Update mechanism

There is no updater. An update is "download a newer llamafile"; each pre-built
llamafile pins the server version it bundles, and the docs tell users this so
they know what they are getting. Versioned GPU libraries live under
`~/.llamafile/v/LLAMAFILE_VERSION`.

The 0.10 line is a from-scratch rebuild on a new build system. `README_0.10.0.md`
lists what was temporarily lost in the move: GPU support for Windows, stable
diffusion, some CLI features, `pledge()` sandboxing, localscore, llamafiler
embeddings. It also documents a stream of fix releases (mmap errors, server
timeouts, CUDA on Linux, Metal). Users who wanted the old behaviour are told to
download 0.9 releases.

Sources: <https://github.com/mozilla-ai/llamafile/blob/main/README_0.10.0.md>,
<https://github.com/mozilla-ai/llamafile/releases>.

Assessment: no update channel means no stale-binary problem and no broken
auto-update, but also no security patching. A user on 0.8.x stays on 0.8.x until
they notice. EZLM's `internal/update` is ahead; the lesson is to keep a rollback
path and to pin the llama.cpp build in the UI, as llamafile does.

## 9. Windows on Arm and AMD/Intel GPUs

**Windows on Arm.** The supported-systems page lists "Windows 10+ (AMD64 only)"
and "Darwin 23.1.0+ (GPU is only supported on ARM64)". There is no native
Windows arm64 build documented; an Arm64 Windows user runs the AMD64 APE under
emulation, with no CUDA and, per the 0.10 notes, Windows GPU support still
maturing. The one tracker hit for "windows on arm" (#257) is a generic
"Resource unavailable" on Windows 11, not an Arm-specific fix. The bundled
CUDA/Vulkan DLLs are explicitly "x86_64 Linux and Windows artifacts only", so on
an aarch64 host (including an ARM64 Linux box with an NVIDIA GPU) the bundled
backends do not apply and GPU support falls back to the runtime path.

**AMD.** ROCm is "still experimental" and not bundled in either download; the
user must fetch `ggml-rocm.so`/`.dll` from Hugging Face and install the ROCm
runtime (on Windows, the AMD HIP SDK, not the driver). Prebuilt targets are
gfx906, gfx942, gfx1030-1032, gfx1100-1103; other cards need a self-build.
Multi-GPU "may be broken on Radeon"; `HIP_VISIBLE_DEVICES=0` is the workaround.

**Intel.** No oneAPI/SYCL backend at all. Intel Arc relies on Vulkan, which is
documented as covering "a lot of the hardware that CUDA and ROCm do not", and
which issue #938 says is inconsistent on Windows.

**NVIDIA.** Bundled CUDA needs compute capability 7.5+ (Turing or newer);
Maxwell/Pascal/Volta get no kernels, and the docs suggest Vulkan or a self-build
with CUDA 12.x. The bundled CUDA library is size-optimized and omits IQ-quant
kernels, so IQ1-IQ4 layers silently stay on the CPU.

Sources: <https://docs.mozilla.ai/llamafile/reference/support>, quickstart
("bundled libraries are x86_64 Linux and Windows artifacts only"),
<https://github.com/mozilla-ai/llamafile/blob/main/README_0.10.0.md>.

## 10. Recommendations for EZLM

**R1 (priority P1, effort M). Add an Anthropic Messages API surface.**
Serve `POST /v1/messages` and `/v1/messages/count_tokens` with `system`,
`stop_sequences`, streaming and Anthropic tool blocks, and accept both
`Authorization: Bearer` and `x-api-key`. llamafile does this and documents it
(<https://docs.mozilla.ai/llamafile/using-llamafile/api>); it is what lets
Anthropic-native coding agents point at the server. EZLM's `internal/serve` has
no `/v1/messages` today, so an agent that only speaks the Anthropic dialect
cannot use an EZLM deployment. This is the single highest-value gap found in
this teardown.

**R2 (P1, effort S). Report the backend that is actually running, and fail loudly
when the requested one did not load.**
llamafile's documented failure mode is a silent CPU fallback: "If any library
loads but reports no usable device, llamafile skips it"; the docs tell users to
force `--gpu nvidia|amd|vulkan` just to get an error, and issue #384 (13
comments) is users unable to tell. EZLM chooses a placement in `internal/fit`
and should verify it after launch (read `/props` or the startup log) and show one
line: backend, layers offloaded, VRAM used. Evidence:
<https://docs.mozilla.ai/llamafile/reference/support>.

**R3 (P2, effort S). Gate CUDA on compute capability and prefer Vulkan
otherwise.**
The bundled CUDA kernels require compute capability 7.5+, and IQ-quant layers
are excluded from the size-optimized library, so a Pascal card or an IQ4 model
partially falls back to CPU with no message. EZLM should read compute capability
during `internal/scan` (or parse `nvidia-smi --query-gpu=compute_cap`) and pick
Vulkan/CPU with a stated reason instead of a CUDA plan that silently degrades.
Evidence: same support page; issue #938 for Vulkan-on-Windows reliability
caveat.

**R4 (P2, effort S). Keep multi-key credentials, and make LAN exposure an
explicit choice.**
llamafile has one `--api-key` and no auth by default; its docs warn that
exposing the server without a key is the common mistake, and that CORS is not
authentication (<https://docs.mozilla.ai/llamafile/using-llamafile/api>). EZLM is
already ahead with named keys (`internal/serve/config.go`), so the work is to
keep that and add a deploy-time check: if the bind address is not loopback and
no key is set, refuse or warn once, in plain language.

**R5 (P2, effort S). Accept any model name in requests and keep a stable alias
per deployment.**
llamafile requires the OpenAI `model` field even with one model loaded and tells
clients to send a placeholder; `--alias` exists to give a stable name. Coding
agents and SDKs hardcode names, so EZLM should answer `/v1/models` with a stable
alias and accept unknown model strings rather than 404, while still using the
key+model pair for port ownership (`internal/serve/port_test.go`). Evidence:
<https://docs.mozilla.ai/llamafile/using-llamafile/api>.

**What not to copy.** No installer, no model picker, no fit calculation, no
update channel, and a 4 GB Windows executable ceiling that forces external
weights for anything interesting. llamafile's "single file, zero daemon" idea is
worth keeping only as an EZLM recovery/portable mode, not as the main flow.
