## First-run flow

1. Download the installer for the OS from <https://lmstudio.ai/download>. Linux ships as an AppImage
   (Ubuntu 20.04+; newer than 22 "not well tested").
2. Open **Discover**, search by keyword, `user/model` or a full Hugging Face URL, and download.
   Quants are listed as separate files (`Q3_K_S`, `Q8_0`, ...); the only guidance is "Choose a 4-bit
   option or higher if your machine is capable enough".
3. Switch to **Chat**, open the model loader, pick the downloaded model, optionally change load
   settings, load, chat.

Source: <https://lmstudio.ai/docs/app/basics>, <https://lmstudio.ai/docs/app/basics/download-model>.

There is no hardware-aware first-run step: no "here is what your machine can run" screen, no
recommended model, no auto-download. The user does the matching. The first screen that mentions
hardware at all is Settings > Hardware, and only if the user goes looking.

## Hardware detection

- Detection lives in **Settings > Hardware**, listing CPU, RAM, and each detected GPU with its
  VRAM. Detection is per-backend: the Vulkan runtime is the one that has to enumerate GPUs, and it
  only enumerates what the Vulkan driver reports.
- Known failure: with a discrete GPU present, the integrated GPU is not listed at all
  (<https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/382>, 25 reactions, 53 comments,
  open since 2025-02-01, assigned, label `needs-investigation`). Reporter: Ryzen 5 8645HS +
  Radeon 760M + RTX 4060 laptop; only the NVIDIA GPU shows.
- Windows on Arm is explicitly supported ("Snapdragon X Elite"), x64 requires AVX2.
- Apple Silicon only for Mac: "Intel-based Macs are currently not supported", pointing at issue #9.

Sources: <https://lmstudio.ai/docs/app/system-requirements>, issue #382 above.

## Model picking

- Catalogue = Hugging Face, filtered to formats LM Studio can run (GGUF via llama.cpp, MLX on
  Apple Silicon). No opinionated ranking, no "best for your machine" list, no task tags.
- The user chooses model *and* quant *and* context length *and* GPU offload manually, or accepts
  per-model defaults. Per-model defaults and config presets exist
  (<https://lmstudio.ai/llms.txt>, "Per-model Defaults" and "Config Presets" sections), so a user
  can save a working configuration and get it back on the next load.
- Speculative decoding needs a matching *draft* model, which the user must find and download
  separately; the UI filters the dropdown to "compatible" draft models and shows "No compatible
  draft models" when the vocabulary check fails
  (<https://lmstudio.ai/llms.txt>, Speculative Decoding section). That filter has produced a stream
  of bugs: #2044 (Gemma 4 MTP drafter indexed but never offered, 26 reactions),
  #1597 (Qwen3.5 dense drafters rejected, 38), #1761 (mmproj invalidates compatibility, 20).

## Memory-fit logic

- Fit is a *load-time* concern, not a *pick-time* one. The loader exposes context length and a GPU
  offload fraction (`gpuOffload` 0-1, `off`, `max`; `lms load --gpu 0.5|max|off`,
  <https://lmstudio.ai/llms.txt> CLI section). The user picks the fraction; LM Studio does not
  search the space for them.
- Runtime memory management is the interesting part and it is stronger than the pick-time story:
  - **JIT loading** (default on): `/v1/models` lists every downloaded model, and an inference call
    loads the model on demand.
  - **Idle TTL**: default 60 minutes; a request refreshes the timer; on expiry the model unloads.
  - **Auto-evict** (default on): unloads previously JIT-loaded models before loading a new one.
  - Documented explicitly for "Zed, Cline, Continue.dev" style clients, i.e. the TTL exists because
    coding agents leave models resident.
- Weak spot: when the requested context does not fit, LM Studio has been reported to load anyway or
  to clamp silently rather than refuse. #2191 "silently loads model 'successfully' when context
  length memory is insufficient" (6 reactions), #2250 "MLX models ignore every user-configured
  context length, context auto-fit always overrides it" (24), #2323 MLX clamps context to 4864 (2).
  #1850 asks for an estimated memory figure in the reload dialog at all (0 reactions, but it is the
  tell: the number is not shown).

Sources: <https://lmstudio.ai/llms.txt> (JIT, TTL, auto-evict, CLI), issues #2191, #2250, #1850.

## OpenAI-compatible server and keys

- Start: Developer tab toggle, or `lms server start`. Default port 1234, base URL
  `http://localhost:1234/v1`.
- Surface area is the widest of any product in this teardown: OpenAI-compatible chat/completions,
  legacy completions, embeddings, `/v1/models`, `/v1/responses`, structured output, tool use; plus
  **Anthropic-compatible `/v1/messages`**, a Jev/TypeSafe `/v1/systemone` and OpenAI-style
  `/v1/decisions` endpoint, a native REST API (`/api/v1/...`) and Python/TS SDKs.
  <https://lmstudio.ai/docs/developer/core/server>
- **Auth is off by default** and only exists from 0.4.0. Turn it on in Server Settings > Require
  authentication, then Manage Tokens: named tokens, per-token permissions, shown once at creation,
  editable and deletable later. Requests use `Authorization: Bearer $LM_API_TOKEN`.
  <https://lmstudio.ai/docs/developer/core/authentication>
- **LAN exposure** is one switch ("Serve on Local Network") that rebinds to a non-localhost address
  and updates the displayed URL; docs warn to enable authentication first and offer
  `lms server start --bind 0.0.0.0`. <https://lmstudio.ai/docs/developer/core/server/serve-on-network>
- Historically users asked for exactly this and had to wait: #561 "API keys to secure the endpoint"
  (24 reactions, open since 2025), #117 "SSL Cert / HTTPS" (26 reactions, 19 comments, still open,
  no TLS). So: bearer tokens yes, TLS no.

## Coding-agent integrations

- No first-party plugin per agent. The integration surface is the URL plus a documented protocol:
  OpenAI `/v1`, Anthropic `/v1/messages`, and the `lmstudio` provider that ships inside Cline,
  Continue.dev and Zed (links to those source files appear in LM Studio's own TTL docs).
- What makes it work for agents is the server behaviour, not a connector: JIT load on first request,
  auto-evict when the agent switches models, TTL so a forgotten session does not hold VRAM, and
  `lms server start` + "run server on login" for headless use.
- MCP is supported in-app and over the API (`integrations` field in `/api/v1/chat`), and there is a
  dedicated "MCP via API" doc page. <https://lmstudio.ai/docs/developer/core/mcp>

## Update mechanism

- App updater: built in on macOS and Windows, checks on launch, offers "update now or later"; the
  Linux in-app updater was late (issue #89) and only landed in 0.4.22 (2026-08-28: "Enabled in-app
  updates for AppImage and `.deb` installations").
- Engines update separately from the app: **LM Runtimes** are individually packaged llama.cpp (and
  MLX) builds, downloadable and hot-swappable since 0.3.0 without an app update
  (<https://lmstudio.ai/llms.txt>; shortcut `Cmd/Ctrl+Shift+R`). The changelog is full of runtime
  bumps (0.4.26 b2 "llama.cpp runtime to 2.50.0 (upstream b11337)"; Bionic 1.2.0 "llama.cpp 2.67.0
  extension packs").
- Cadence: roughly weekly point releases (0.4.22 Aug 28, 0.4.24 Sep 9, 0.4.25 Sep 19, 0.4.26 Oct
  13, 0.4.27 Oct 29, 0.4.28 Oct 31) plus betas.
- Failure modes visible in the changelog itself: "[Mac] Fixed 'Restart to apply update' reopening the
  current version instead of installing the update" (0.4.28 b2, i.e. the updater could no-op);
  "Fixed app updater redownloaded unnecessarily" (Bionic 1.2.0); "Fixed runtime discovery
  reliability" (0.4.27); "Fixed compatibility checks for M5-only Metal runtimes" (0.4.27). Runtime
  and app versions drift apart, and the compatibility check is the thing that breaks.
- Strategic note: LM Studio now ships a second app, **Bionic** (agent/IDE-ish, 1.1.x → 1.2.0), which
  reuses LM Studio for inference and adds "LM Link" for remote devices. Two apps, one engine, shared
  CLI — the opposite of a single-binary deployer.

## Windows on Arm, AMD, Intel

**Windows on Arm.** Supported on paper (Snapdragon X Elite, x64 needs AVX2). In practice the GPU
path has been the problem: 0.4.26 build 5 is literally "Fix Windows on ARM CUDA not detected", and
build 3 is "Added CUDA 13 support on Windows ARM" (<https://lmstudio.ai/changelog/lmstudio>). So
until late Oct 2026, WoA users had a working CPU path and a broken/missing CUDA path; the
Adreno/Qualcomm path is not a documented runtime at all. 153 issues match arm64/snapdragon/"windows
on arm".

**AMD.** ROCm runtime exists but detection and currency are recurring: 0.4.27 "Added Radeon 8065S
detection for ROCm runtime compatibility" (a GPU shipped and went undetected until a point release),
#1394 "Update ROCm" (30 reactions) is a standing request to track upstream, #250 asks for a Ryzen AI
build on Linux. Vulkan is the fallback and is the largest keyword bucket (281 issues).

**Intel.** No SYCL, no OpenVINO, no NPU path. Intel users get Vulkan, which the SYCL requester says
is 2-3x slower (#171), and Vulkan on Intel is where the iGPU-not-detected bug bites (#382). Three
separate open feature requests (#171 SYCL 59, #581 NPU 45, #2025 OpenVINO 29) all say the same
thing: the hardware is there and the app ignores it.

## How this compares to EZLM

Read for comparison (not edited): `internal/fit/fit.go`, `internal/keys/keys.go`,
`internal/serve/config.go`, `internal/update/update.go`, `internal/scan/`.

- EZLM's planner already searches quant x context x KV type x placement (GPU / hybrid
  `--n-cpu-moe` / split / CPU) and ranks by effective intelligence, with a hard OS memory floor
  (`internal/fit/fit.go:1-60`, `ComputeBudgets`, `Plans`, `UtilityFor`). LM Studio does none of
  that search; it asks the user for a GPU-offload fraction. EZLM is ahead here and should not copy
  LM Studio's loader.
- EZLM generates named API keys with a `ezlm-` prefix (`internal/keys/keys.go:11`), keeps a named
  key list (`internal/serve/config.go:20-32`) and can bind all interfaces
  (`internal/serve/config.go:94`). LM Studio's per-token *permissions* and show-once UX are the
  parts EZLM does not have.
- EZLM has no equivalent of LM Studio's JIT load + idle TTL + auto-evict. Every LM Studio coding
  agent integration story rests on those three, and EZLM currently has no idle unload at all
  (grep for `ttl` in `internal/serve`, `internal/engine` finds only a download-idle timer in a test).

## Recommendations for EZLM

**R1. Idle TTL plus auto-evict on the served model. Priority P1, effort M.**
Evidence: LM Studio documents TTL (default 60 min), auto-evict and JIT loading precisely for
"Zed, Cline, Continue.dev" clients, and shipped them in 0.3.9 after users complained models stayed
resident (<https://lmstudio.ai/llms.txt>; <https://lmstudio.ai/blog/lmstudio-v0.3.9>). EZLM loads a
model and leaves it. A one-click deployer that a coding agent talks to will hold VRAM forever the
first time the agent crashes. Touches `internal/serve/run.go`, `internal/engine`.

**R2. Show the fit verdict where the model is chosen, and refuse to over-commit. Priority P1, effort S.**
Evidence: LM Studio's pick-time story is the weakest part of its UX and users notice: #1850 (no
estimated memory shown), #2191 ("silently loads model successfully" when context does not fit),
#2250 (context auto-fit overrides the user). EZLM already computes `GPUNeed`/`RAMNeed`/`GPUBudget`
per plan in `internal/fit/fit.go`; printing "this fits, 11.2 of 16 GB" next to each choice, and
failing loudly when a manual context would not fit, is cheap and directly answers the complaint LM
Studio has not answered.

**R3. Per-key scopes and a show-once token flow. Priority P2, effort S-M.**
Evidence: LM Studio 0.4.0 added named tokens with permissions, shown once, plus a per-server
"require authentication" switch that is off by default, and its docs tell users to enable auth before
"Serve on Local Network" (<https://lmstudio.ai/docs/developer/core/authentication>). Users had asked
for keys since 2025 (#561, 24 reactions). EZLM already has named keys; adding read-only vs full
scopes and surfacing the key once (not re-readable from the settings pane) closes the gap, and pairs
with an explicit warning when binding `0.0.0.0`.

**R4. Hot-swappable engine builds, selected per machine, with rollback. Priority P2, effort L.**
Evidence: LM Studio's "LM Runtimes" let llama.cpp be downloaded and hot-swapped without an app update
since 0.3.0, and its changelog shows why that matters: ROCm detection fixes (0.4.27), WoA CUDA fixes
(0.4.26 b5), "runtime discovery reliability", "compatibility checks for M5-only Metal runtimes", and
a stream of issues where a runtime bump breaks model loading (#1741, #2037). EZLM installs one engine
and updates it with the app, so a bad llama.cpp bump forces a full app release. Decoupling them lets
EZLM ship a GPU fix without shipping an installer.

**R5. Ship an Anthropic-compatible `/v1/messages` alongside the OpenAI surface. Priority P3, effort M.**
Evidence: LM Studio serves OpenAI chat/completions, responses, embeddings, Anthropic `/v1/messages`,
and a Jev/TypeSafe endpoint from the same port (<https://lmstudio.ai/docs/developer/core/server>).
Coding agents increasingly speak Anthropic Messages first; a deployer that only offers `/v1` makes
the user hand-edit a base URL that the agent may not accept. EZLM's serve layer already routes
`/v1`; a second translator in `internal/serve` is bounded work.
