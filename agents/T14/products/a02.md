# Ollama (a02)

Desk study, no product installed. Every claim below is from a public page or a GitHub issue,
fetched on 2026-11-06. Ollama's current release at the time of writing is v0.40.15, published
2026-11-03 ([releases](https://github.com/ollama/ollama/releases), accessed 2026-11-06).

Ollama is the closest competitor to EZLM's core promise: one install, a local
OpenAI-compatible endpoint, no configuration. Its weaknesses are the mirror image of EZLM's
strengths: it does not pick a model for the machine, it sizes context from a crude VRAM tier,
and its local API has no authentication.

## First-run flow

- Download for macOS, Windows or Linux, open the app, or run `ollama` in a terminal. "Follow
  the setup prompts. Sign in to use cloud models, or choose a local model."
  ([quickstart](https://docs.ollama.com/quickstart), accessed 2026-11-06).
- The desktop app is now a first-class surface: a chat window, an **Apps** tab that connects
  Claude Desktop and ChatGPT Desktop, and **Settings → Apps** to choose which models those
  apps see. Context length has a slider in app settings
  ([context length](https://docs.ollama.com/context-length), accessed 2026-11-06).
- Windows installs per-user, no Administrator, `%LOCALAPPDATA%\Programs\Ollama`, models in
  `%HOMEPATH%\.ollama`, at least 4 GB for the binary alone
  ([windows](https://docs.ollama.com/windows), accessed 2026-11-06). The app starts in the
  tray and runs a server in the background.
- Linux is a shell script (`curl -fsSL https://ollama.com/install.sh | sh`), which installs a
  systemd unit ([faq](https://docs.ollama.com/faq), accessed 2026-11-06).
- Sign-in is optional for local models and required for cloud models. `ollama signin`
  authenticates cloud requests ([authentication](https://docs.ollama.com/api/authentication),
  accessed 2026-11-06). This is the one place Ollama asks for an account; EZLM's beta does not.

First-run gap for EZLM: Ollama asks the user to choose a model by name from a library, it does
not answer "what should I run on this laptop". EZLM's whole pitch is that answer.

## Hardware detection

- The server scans at startup and logs an "inference compute" block listing the detected
  library and device. It ships multiple LLM libraries compiled for different GPUs and CPU
  vector features and picks the best one; if detection is wrong the user can force
  `cpu_avx2`, `cpu_avx` or `cpu`
  ([troubleshooting](https://docs.ollama.com/troubleshooting), accessed 2026-11-06).
- Supported backends: CUDA (compute capability 5.0+, driver 550+; 5.0–6.2 need 570+), ROCm
  v7 on Linux and Windows, Metal on Apple GPUs, and Vulkan for "additional GPU support on
  Windows and Linux", enabled by default when the backend is installed
  ([hardware support](https://docs.ollama.com/gpu), accessed 2026-11-06).
- Vulkan is how Intel Arc and unsupported AMD cards get acceleration. The same page warns
  that Vulkan needs root or extra capabilities to report *available* VRAM; without that,
  "Ollama will use approximate sizes of the models to make best effort scheduling decisions."
  That is a direct memory-fit risk, not just a detection detail.
- Multi-GPU selection is by `CUDA_VISIBLE_DEVICES`, `ROCR_VISIBLE_DEVICES` or
  `GGML_VK_VISIBLE_DEVICES`; the docs recommend UUIDs over indices on NVIDIA.
- Detection failures are documented, not hidden: a Linux suspend/resume can lose the NVIDIA
  GPU until `nvidia_uvm` is reloaded, and some RDNA2/RX 6000 systems on Windows do not expose
  ROCm v7, so Vulkan is the recommended fallback.

## Model picking

- There is no documented automatic recommendation. `ollama run gemma4` runs a named model
  and tag ([cli](https://docs.ollama.com/cli), accessed 2026-11-06); the library at
  [ollama.com/library](https://ollama.com/library) (accessed 2026-11-06) lists sizes and
  tags, and the user picks. The app's setup prompts ask the user to choose a local model.
- Defaults are by tag: a bare name resolves to `latest`, which is convenient but means the
  model can change under the user when the library moves a tag. The docs do not describe a
  pin or lock file for a deployed model.
- Cloud models are mixed into the same namespace (`gemma4:31b` can be cloud or local), with
  sign-in deciding which runs. Good for demos, confusing for "is this local?".
- The model list is the discovery surface, not the hardware. A 4 GB laptop and a 24 GB GPU
  see the same library; only the downloaded size and the runtime scheduler differ.

## Memory-fit logic

- The scheduler loads a model into available memory, offloads what does not fit to CPU, and
  serves it with a processor split the user can inspect with `ollama ps` (`PROCESSOR` column,
  `UNTIL` for unload) ([context length](https://docs.ollama.com/context-length), accessed
  2026-11-06). `ollama ps` is the only built-in answer to "is this running on my GPU?".
- Context is chosen from total VRAM, not from the model or the workload: `< 24 GiB VRAM: 4k
  context`, `24–48 GiB: 32k`, `>= 48 GiB: 256k`, overridable with
  `OLLAMA_CONTEXT_LENGTH`. The docs themselves say coding and agent tasks "should be set to
  at least 64000 tokens" ([context length](https://docs.ollama.com/context-length), accessed
  2026-11-06). So the default on every consumer GPU with less than 24 GB is 4k, and the
  agent use case the docs recommend needs 64k. That is the single biggest fit gap.
- Parallelism multiplies memory: `OLLAMA_NUM_PARALLEL` defaults to 1 and "required RAM will
  scale by OLLAMA_NUM_PARALLEL * OLLAMA_CONTEXT_LENGTH"; `OLLAMA_MAX_LOADED_MODELS`
  defaults to 3 per GPU ([faq](https://docs.ollama.com/faq), accessed 2026-11-06). Keeping
  three models warm on a 12 GB card is a common way to hit an out-of-memory error.
- The model stays loaded for 5 minutes after a request by default (`keep_alive`), which holds
  VRAM while the user does something else. `ollama stop` unloads it.
- There is no safety margin for the OS and no "this plan will not starve the desktop" promise.
  Scheduling is best effort, and on Vulkan the VRAM number can be an estimate.

Compare EZLM: `internal/fit/fit.go:89` tries 64k, 32k, 16k and 8k contexts per model, quant
and KV type; `internal/fit/fit.go:171-217` subtracts an OS floor and a safety margin before
it will call a plan usable. EZLM is materially stronger here. The gap is presentation: EZLM
should show the same `PROCESSOR`-style truth Ollama shows after a deploy.

## OpenAI-compatible server and keys

- Local server on `http://localhost:11434`, OpenAI-compatible under `/v1`
  (`/v1/chat/completions`, `/v1/models`, `/v1/embeddings`, plus Responses in recent
  releases) and an Anthropic-compatible `/v1/messages`
  ([OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility), accessed
  2026-11-06; [Claude Code](https://docs.ollama.com/integrations/claude-code), accessed
  2026-11-06).
- The local API "does not require authentication". OpenAI clients must pass *some* key value
  but "Ollama ignores it" ([authentication](https://docs.ollama.com/api/authentication),
  accessed 2026-11-06). API keys exist only for `https://ollama.com/api` and
  `https://ollama.com/v1` cloud access, as `Authorization: Bearer`.
- Binds `127.0.0.1:11434` by default. LAN exposure is `OLLAMA_HOST=0.0.0.0:11434`, still
  with no auth ([faq](https://docs.ollama.com/faq), accessed 2026-11-06). CORS defaults to
  127.0.0.1 and 0.0.0.0 origins, widened with `OLLAMA_ORIGINS`.
- Net effect: the zero-friction default is excellent, and the moment a user shares the port
  on a LAN there is an unauthenticated inference endpoint on the network. Users asked for
  auth in 2023 ([#1053](https://github.com/ollama/ollama/issues/1053), 75 reactions, 25
  comments, closed); the local server still has none.

Compare EZLM: `internal/serve/config.go:115-122` passes `--api-key` and an explicit `-c`
context to llama-server, and `internal/keys/keys.go:12` generates an `ezlm-` key (~238 bits).
`internal/serve/config.go:100-108` separates the loopback URL from the optional LAN URL. EZLM
is safer by default but noisier to set up; the Ollama lesson is to make the key copyable in
one click, not to remove it.

## Coding-agent integrations

This is Ollama's strongest move and the one EZLM should copy first.

- `ollama launch` configures and starts an external app against the local server;
  `ollama launch claude`, `ollama launch codex`, `ollama launch opencode`
  ([cli](https://docs.ollama.com/cli), accessed 2026-11-06). For Claude Code, Ollama offers
  to install it if missing, then points it at the Anthropic-compatible endpoint
  ([quickstart](https://docs.ollama.com/quickstart), accessed 2026-11-06).
- The integrations index lists more than twenty apps across coding, IDEs, chat, RAG and
  automation: Claude Code, Codex, OpenCode, Cline CLI, Copilot CLI, Droid, Goose, VS Code,
  Cline, JetBrains, Roo Code, Xcode, Zed, n8n, Onyx, and others
  ([integrations](https://ollama.com/integrations), accessed 2026-11-06).
- Claude Code gets tool calling, file edits, subagents, web search/fetch, vision and thinking
  through the same endpoint ([Claude Code](https://docs.ollama.com/integrations/claude-code),
  accessed 2026-11-06). That is a much larger claim than "OpenAI-compatible URL".
- The context default works against this: an agent that sends a 10k-token prompt to a 4k
  default gets a silent truncation, which is exactly the failure mode tracked in
  [#1005](https://github.com/ollama/ollama/issues/1005) and
  [#7043](https://github.com/ollama/ollama/issues/7043).

EZLM today hands the user a URL and a key. `ollama launch` shows the better onboarding: detect
the agent, write its env vars, start it, and only then show the URL for everything else.

## Update mechanism

- macOS and Windows: the app downloads updates automatically and the tray item offers
  "Restart to update"; manual download is also possible. Linux: re-run the install script
  ([faq](https://docs.ollama.com/faq), accessed 2026-11-06). Windows keeps downloaded
  updates and `upgrade.log` under `%LOCALAPPDATA%\Ollama`
  ([windows](https://docs.ollama.com/windows), accessed 2026-11-06).
- There is no documented version pin or downgrade path, and no documented "update later"
  control beyond the restart prompt. Users have asked to disable auto-update
  ([#6024](https://github.com/ollama/ollama/issues/6024), 28 reactions, 5 comments, open) and
  to stop the app starting at login ([#162](https://github.com/ollama/ollama/issues/162), 123
  reactions, 67 comments, open).
- Release cadence is high: v0.40.13 on 2026-10-29, v0.40.14 on 2026-11-03, v0.40.15 on
  2026-11-03 ([releases](https://github.com/ollama/ollama/releases), accessed 2026-11-06).
  Frequent automatic updates on a beta product are a real regression surface.

Compare EZLM: `internal/update/update.go:56` only *checks* GitHub releases and returns an
`Info`; the user chooses. That is the safer default. The Ollama lesson is to add a visible
"update now / later" and a rollback note, not to auto-apply.

## What breaks on Windows on Arm and on AMD/Intel GPUs

**Windows on Arm.** There is a native `ollama-windows-arm64.zip` asset in v0.40.15
([release assets](https://api.github.com/repos/ollama/ollama/releases?per_page=8), accessed
2026-11-06), so the CLI runs natively. But the Windows docs promise NVIDIA and AMD Radeon
acceleration only, and the open Snapdragon request says the NPU and Adreno GPU are not used
([#5360](https://github.com/ollama/ollama/issues/5360), 81 reactions, open since 2024-06-28).
Expect CPU-only inference on a Snapdragon X Elite, which is slow for anything agent-sized.
For EZLM: do not claim GPU acceleration on WoA until it is measured; the safe default is a
small model and a CPU speed estimate.

**AMD.** ROCm v7 is required. On Windows the supported list is short (RX 7900/7800/7700/7600
and the W-series); Linux adds 9000-series and Ryzen AI. Some RX 6000 systems "may not expose
ROCm v7 on current Windows AMD drivers", and Vulkan is the recommended fallback. Mixed
iGPU/dGPU systems can select an unstable Vulkan iGPU; the workaround is
`GGML_VK_VISIBLE_DEVICES`
([windows](https://docs.ollama.com/windows), [hardware support](https://docs.ollama.com/gpu),
accessed 2026-11-06). Older cards need `HSA_OVERRIDE_GFX_VERSION` guesswork.

**Intel.** Acceleration is Vulkan only; the Arc support request has been open since 2023 with
139 reactions ([#1590](https://github.com/ollama/ollama/issues/1590)). Vulkan on Intel also
hits the approximate-VRAM scheduling caveat above, so fit decisions are less reliable than on
CUDA.

## Recommendations for EZLM

**R1. Make the deployed plan visible, in `ollama ps` terms. Priority P1, effort S.**
Show context length, processor split (GPU/CPU layers) and tokens/sec after every deploy, the
way `ollama ps` shows `PROCESSOR` and `UNTIL`. Evidence: Ollama documents `ollama ps` as the
way to verify the split and context ([context length](https://docs.ollama.com/context-length),
accessed 2026-11-06); users cannot otherwise tell a 4k CPU-offloaded deploy from a 64k GPU one.
EZLM already computes every number (`internal/fit/fit.go`, `Plan.Ctx`, `Plan.NGL`,
`Plan.TokPerSec`); this is a UI/serialization change in the status payload, not new logic.

**R2. Copy `ollama launch` for coding agents. Priority P1, effort M.**
One command or one button that detects Claude Code, Codex or OpenCode, writes its base URL,
key and model env vars, and starts it. Evidence: `ollama launch claude|codex|opencode`
([cli](https://docs.ollama.com/cli), accessed 2026-11-06) plus a 20+ app integration index
([integrations](https://ollama.com/integrations), accessed 2026-11-06). EZLM's `internal/integrate`
is the natural home; the user-facing win is removing the copy-paste step that EZLM currently
requires.

**R3. Publish the context/memory tradeoff instead of a tier default. Priority P1, effort S.**
Ollama picks 4k/32k/256k from total VRAM, while its own docs say agents need 64k. Show the
user "64k context costs X GB, this plan fits with Y GB spare" and let them move it. Evidence:
[context length](https://docs.ollama.com/context-length) (accessed 2026-11-06);
[#1005](https://github.com/ollama/ollama/issues/1005), 87 reactions. EZLM's `ctxLadder` and
`ComputeBudgets` already produce the data; the gap is exposing it.

**R4. Keep the API key, and make LAN exposure require it. Priority P2, effort S.**
Ollama binds loopback with no auth, and `OLLAMA_HOST=0.0.0.0` exposes an unauthenticated
inference endpoint; users asked for auth in 2023 ([#1053](https://github.com/ollama/ollama/issues/1053),
75 reactions). EZLM already generates `ezlm-` keys (`internal/keys/keys.go:12`) and passes
`--api-key` (`internal/serve/config.go:121`). Make the key one-click copyable, show it on the
LAN screen, and add a rotate action.

**R5. Treat Vulkan VRAM as an estimate and leave headroom. Priority P2, effort S.**
Ollama says Vulkan may only report approximate model sizes when it cannot read available VRAM,
and Vulkan output corruption is reported on AMD iGPUs
([hardware support](https://docs.ollama.com/gpu), [#15261](https://github.com/ollama/ollama/issues/15261)).
EZLM's fit margins (`internal/fit/fit.go:198-217`) already leave an OS floor; on Windows AMD
and Intel paths, widen the margin and prefer a smaller context rather than a partial offload
that stutters. This is a one-line policy change plus a test.

**R6 (stretch). Offer update-now/later and a pin. Priority P3, effort S.**
Ollama auto-updates and users ask to disable it ([#6024](https://github.com/ollama/ollama/issues/6024),
28 reactions; [faq](https://docs.ollama.com/faq)). EZLM's `internal/update/update.go:56` only
checks, which is better; add a visible defer and a way to stay on a known-good version.

## Open questions

- Does the Ollama app recommend models from detected memory, or only list the library? The
  quickstart shows a choice, not a recommendation; not verified on a machine (desk study).
- Reddit and forum counts: reddit.com's JSON endpoint returned an HTML block page from this
  network, so the complaint table is GitHub-only. A follow-up pass from a browser could add
  r/ollama counts.
- Exact default `keep_alive` (5m) is widely reported but I did not find it stated on a docs
  page fetched today; the FAQ documents the parameter and `ollama stop`, not the default.
