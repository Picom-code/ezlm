# GPT4All (agent a04)

All sources read 2026-11-06. GPT4All is Nomic's MIT-licensed desktop chat app plus a
`llama.cpp`-based backend and Python bindings. This section covers the desktop app
(`gpt4all-chat`), because that is the product EZLM competes with.

The release cadence matters: no desktop release in the 20 months before this
teardown, and no code commit in the 17 months before it. The app is not archived,
but it is effectively in maintenance freeze. Everything below should be read as
"the state GPT4All froze in", not as a moving target.

## First-run flow

1. Install from gpt4all.io (Windows x64, Windows ARM, macOS, Ubuntu `.run`).
2. Open the app, press **Start Chatting** on the home page.
3. Press **+ Add Model**, search Hugging Face or pick a curated model, press **Download**.
4. Return to Chats, press **Load Default Model**, start typing.

Sources: https://docs.gpt4all.io/gpt4all_desktop/quickstart.html,
https://docs.gpt4all.io/gpt4all_desktop/models.html.

There is no machine scan and no recommendation. The user is told "we recommend
starting with Llama 3" in the docs, but the app itself does not know whether that
model fits the machine. The default model list is a download browser, not a plan.
Six manual steps from install to first token, of which step 3 is the one a novice
gets wrong (4.66 GB download that may not fit).

The one good idea here is **Load Default Model**: after the first download the
app remembers a default, so later launches are one click. EZLM gets the same
effect by restoring the running model at startup.

## Hardware detection

- The app detects the platform and offers a **Device** setting: `Auto`, `Metal`
  (Apple Silicon), `CPU`, `GPU`. Default `Auto`.
  https://docs.gpt4all.io/gpt4all_desktop/settings.html
- GPU backends are CUDA (NVIDIA), Metal (Apple), and Vulkan (NVIDIA/AMD/Intel).
  The Vulkan backend is Nomic's own ("Nomic Vulkan", announced 2023-09-18 in the
  README).
- It does **not** report RAM, VRAM, or free memory anywhere in the UI. There is
  no pre-download fit check; the only RAM guidance is a `RAM Required` column in
  the docs' example table (4.66 GB file -> 8 GB RAM, 7.37 GB file -> 16 GB).
  https://docs.gpt4all.io/gpt4all_desktop/models.html
- CPU thread count is a manual setting, default 4.

## Model picking

- Curated list plus live Hugging Face search, sortable by likes, downloads, or
  upload date. Users pick a repo and a file; no quant guidance beyond the docs'
  paragraph that smaller quants are faster and slightly worse.
- No "recommended for your machine" state, no score, no capability tags. The
  user is choosing by name and download count.
- Supported architectures are whitelisted in code, so new architectures need a
  new app build. That is the root cause of the model-support lag below.
- Remote providers (OpenAI, Groq, Mistral, OpenRouter-style endpoints) are a
  separate tab since v3.10.0; they are a convenience, not the local path.

## Memory-fit logic

There is no planner. The user sets, per model:

- **GPU Layers** (default 32), **Context Length** (default 2048), **Prompt Batch
  Size** (128), **CPU Threads** (4).
  https://docs.gpt4all.io/gpt4all_desktop/settings.html

The app loads the GGUF and lets `llama.cpp` fail if the machine is short. The
troubleshooting page's only "Error Loading Models" advice is that the weights may
be incompatible and to try an officially supported model; memory exhaustion is not
mentioned at all. https://docs.gpt4all.io/gpt4all_help/troubleshooting.html

Consequences visible in the tracker:

- #2808 "Can't change GPU Layers setting for any model with a number larger than
  default" (open since 2024-08-07, 2 reactions): the field silently reverts to 32.
  https://github.com/nomic-ai/gpt4all/issues/2808
- #2289 "Searching for models returns f32 models and no option to select the
  quant size" (3 reactions). https://github.com/nomic-ai/gpt4all/issues/2289

So the fit knobs exist but are unreliable and unexplained, and the model browser
does not use them.

## OpenAI-compatible server and keys

- **Off by default.** Settings has "Enable Local Server" and "API Server Port"
  (default 4891). https://docs.gpt4all.io/gpt4all_desktop/settings.html
- **No API key.** The server checks no `Authorization` header at all; a `curl`
  with no auth works. Source: `gpt4all-chat/src/server.cpp` (read 2026-11-06),
  which registers `/v1/models`, `/v1/completions`, `/v1/chat/completions` and
  never reads an auth header.
- **Localhost only.** It binds `QHostAddress::LocalHost` (server.cpp line 464),
  so LAN clients cannot reach it. There is no setting to change the bind address.
  Requested in #3491 "Windows API server doesn't bind to correct interface"
  (open, 2025-02-13, 2 reactions): the reporter wants `0.0.0.0` and cannot get
  it. https://github.com/nomic-ai/gpt4all/issues/3491
- **Narrow API surface.** The request parser rejects `stream: true`, `stop`,
  `seed`, `logprobs`, `logit_bias`, `response_format`, `tools`, `tool_choice`,
  `function_call` and `functions` with an explicit "not supported" error
  (server.cpp lines ~160-190 and ~405-420). No streaming means every coding-agent
  client that expects SSE falls back to a non-streaming path or breaks.
- The older Docker "GPT4All API Server" is a separate product with its own docs
  (https://docs.gpt4all.io/gpt4all_api_server/home.html); do not confuse the two.

This is the weakest dimension. EZLM already has a bearer key (`ezlm-` + 40
base62 chars), an explicit LAN toggle, and a `/v1/models` self-check; GPT4All has
none of the three.

## Coding-agent integrations

There is no official integration page and no per-client snippet. What exists:

- Generic "OpenAI-compatible" claim in the FAQ and settings.
- #2174 "Incompatible with continuedev chat and code completion" (open since
  2024-03-27, 8 reactions, 14 comments): Continue auto-detects the server and the
  model, then receives empty responses, while the same setup works against Ollama
  and KoboldCpp. https://github.com/nomic-ai/gpt4all/issues/2174
- #3546 "[Feature] Add MCP Server Support for Local Inference" (open, 52
  reactions, the most-reacted open issue in the repo):
  https://github.com/nomic-ai/gpt4all/issues/3546

The empty-response report is consistent with the parser's `stream`/`tools`
rejections: a client that sends either gets an error object, and some clients
render that as an empty message. That link is inference, not something the thread
proves.

## Update mechanism

Qt Installer Framework with a maintenance tool, plus an in-app update check
against Nomic's release feed.

- The macOS maintenance tool crashed on Sequoia until v3.7.0 signed it:
  "Sign the maintenance tool on macOS to prevent crash on Sequoia" (CHANGELOG
  3.7.0). https://github.com/nomic-ai/gpt4all/blob/main/gpt4all-chat/CHANGELOG.md
- v3.2.0 fixed "comparison of pre- and post-release versions for update check",
  i.e. the version comparator itself was wrong at least once.
- v3.3.0: "The offline update button now directs users to the offline installer
  releases page."
- The Windows uninstaller is separately broken: #3099 "Uninstaller doesn't run on
  Windows 11" (open since 2024-10-15, 6 reactions, 7 comments).
  https://github.com/nomic-ai/gpt4all/issues/3099

The lesson is not "copy the Qt installer"; it is that upgrade and uninstall paths
need their own tests, and that the version comparator is a bug surface.

## Windows on Arm and AMD/Intel GPUs

**Windows on Arm**

- A separate `-win64-arm` installer exists since v3.7.0 and is CPU-only: "Support
  for GPU and/or NPU acceleration is not available at this time. Only the CPU will
  be used to run LLMs." CHANGELOG 3.7.0.
- The README says the Windows ARM build "supports Qualcomm Snapdragon and
  Microsoft SQ1/SQ2 processors".
- `gpt4all-chat/system_requirements.md` says "Windows and Linux PCs with ARM CPUs
  are not currently supported" — directly contradicting the README and the
  shipped installer. One of the two is stale; a new user cannot tell which.
- v3.9.0 fixed two WoA-specific bugs: graphical artifacts on some SoCs, and a
  crash adding PDFs to LocalDocs. These are the kinds of bugs CPU-only ARM users
  hit and X64 users never see.

**AMD / Intel GPUs**

- The path is Vulkan, not ROCm and not oneAPI. There is no ROCm backend.
- Minimum GPU in `system_requirements.md` is "Anything Direct3D 11/12 or OpenGL
  2.1 capable", which is a very low bar and does not mean "runs well".
- Vulkan support is per-architecture and lags: v3.9.0 added OLMoE and Granite MoE
  "no Vulkan", i.e. CPU-only for those; earlier releases added Vulkan for some
  architectures and not others (CHANGELOG 3.1.0, 3.4.0).
- #3144 "Inconsistant AMD Vulkan Performance" on a Radeon 7700S: 40 tok/s
  dropping to 3-4 tok/s between runs, GPU reported at full utilisation.
  https://github.com/nomic-ai/gpt4all/issues/3144
- #2768 "Vulkan: Meta-Llama-3.1-8b-128k slow generation" (2 reactions, 15
  comments). https://github.com/nomic-ai/gpt4all/issues/2768
- #1354 "Support Metal or Vulkan on Intel Macs" (open since 2023, 1 reaction).

## Comparison with EZLM

| Dimension | GPT4All 3.10.0 | EZLM (this snapshot) |
|---|---|---|
| First run | 6 manual steps, user picks and downloads | scan -> plan -> deploy, one click |
| Hardware detection | device class only (Auto/Metal/CPU/GPU) | CPU, RAM, disk, per-GPU VRAM, GPU processes (`internal/scan`) |
| Model picking | name/downloads, no fit filter | catalog of 32 scored models, fit-ranked (`internal/catalog`, `internal/fit`) |
| Memory fit | manual GPU layers/ctx, load-time failure | quant x ctx x KV x placement search with RAM/VRAM budgets (`internal/fit`) |
| Server | off by default, no key, localhost only, no streaming/tools | on after deploy, `ezlm-` bearer key, LAN toggle, `/v1/models` self-check (`internal/serve`, `internal/keys`) |
| Coding agents | no snippets; Continue broken (#2174) | not yet verified per client |
| Updates | Qt maintenance tool, in-app check, broken uninstaller | GitHub release check + asset download (`internal/update`) |
| Windows ARM | separate CPU-only build, docs contradict | native Go engine; GPU story unproven |

EZLM is ahead on every row except update polish and (possibly) per-client
documentation. The transferable lessons are therefore mostly about **what happens
when the model catalog is baked into the binary** and **what a thin OpenAI surface
costs you with coding agents**.

## Recommendations for EZLM

**1. Make the model catalog refreshable without an app update. Priority P1, effort M.**
GPT4All's top complaint cluster is new-model support (#3576 Qwen3, #3540 Gemma 3,
#3657 Qwen3.5, #1747 Mixtral), and the fix each time is a new whitelist entry plus
a release; with the last release in Feb 2025 those users are stranded. EZLM has
the same structural risk: `internal/catalog/catalog.json` is embedded in the
binary and `internal/update` only replaces the app. Ship a signed, versioned
catalog fetched at startup (fall back to the embedded copy offline), so a new
model or quant is a data change, not a release. This is the single highest-value
item in this teardown.

**2. Put the fit answer in the model browser. Priority P1, effort S.**
GPT4All documents a `RAM Required` column but the app never checks it, and the
GPU-layers field silently reverts (#2808). EZLM already computes the plan; show
it where the choice is made: per model "fits at 8K ctx, ~24 tok/s" or "needs
2.1 GB more VRAM", and one line of why the default was chosen. Files:
`internal/fit/fit.go` (expose the chosen plan's headroom), model browser in
`internal/web`. No new logic, just surfacing.

**3. Treat the OpenAI surface as a contract and test it against real agents.
Priority P1, effort M.**
GPT4All's server rejects `stream`, `tools`, `tool_choice` and `response_format`
outright (server.cpp), and its most-reacted client bug is Continue.dev returning
empty responses (#2174, 8 reactions). EZLM should run a small conformance suite
(streaming SSE, tool calls, stop sequences, usage counts) against Continue, Cline
and one Zed/OpenAI client, and publish copy-paste config per client. Files:
`internal/serve` (conformance test), docs. This also de-risks the LAN story.

**4. Add an MCP endpoint or at least document the gap. Priority P2, effort M.**
#3546 is the most-reacted open issue in GPT4All (52 reactions) and has been open
since 2025-03. Local-first users increasingly expect their editor/agent to reach
the local model through MCP. EZLM does not need to win this, but a minimal
`/mcp` bridge or a documented "point your MCP client at this URL" section is cheap
differentiation against a frozen competitor.

**5. Test upgrade, downgrade and uninstall as first-class paths. Priority P2, effort S.**
GPT4All's update history is a list of packaging bugs: maintenance tool crash on
macOS Sequoia (fixed in 3.7.0), wrong version comparison (fixed in 3.2.0), and a
Windows 11 uninstaller that does not run (#3099, 6 reactions, open since
2024-10). EZLM's `internal/update` downloads and replaces the app; add tests for
"same version", "older release", "asset missing", and a documented uninstall that
removes models and the `ezlm-` key. Files: `internal/update`, installers.

**6 (stretch). Say what Windows on Arm can actually do. Priority P3, effort S.**
GPT4All ships a CPU-only WoA build and then contradicts itself in its own docs
(README says supported, `system_requirements.md` says not supported). EZLM's scan
should classify WoA explicitly and show "CPU only, expect ~N tok/s" before a
multi-GB download. Files: `internal/scan`, `internal/fit` speed estimate.
