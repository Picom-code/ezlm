# LocalAI (mudler/LocalAI)

Desk study, no install. Version reviewed: **4.12.1** (released 2026-10-23, latest at the time of
writing). All URLs accessed **2026-11-06**. GitHub counts come from the GitHub REST/search API on
that date: `reactions` is the issue's total reaction count, `comments` the comment count, and both
are quoted as `rN/cM`.

## First-run flow

LocalAI is not a desktop app on most platforms; it is a server you start, then a web UI you open.

- Install methods, in the project's own order of preference: **containers (recommended)**, macOS
  DMG, Linux binaries, Kubernetes, build from source. There is no Windows installer and no Windows
  install page at all. https://localai.io/docs/installation/
- The canonical first run is one command: `docker run -p 8080:8080 --name local-ai -ti
  localai/localai:latest`, then open `http://localhost:8080`, go to **Models -> Explore**, search
  `qwen3-4b`, click **Install**, then **Chat**. The CPU image ships no models.
  https://localai.io/docs/basics/getting_started/
- Model install from the gallery is where the magic happens: LocalAI detects the GPU and pulls the
  matching backend OCI image (llama.cpp CUDA/ROCm/SYCL/Vulkan/CPU) on demand. Backends are separate
  images, "pulled only when a model needs it". https://localai.io/docs/features/gpu-acceleration/
  and https://github.com/mudler/LocalAI#readme
- macOS is the one real app: a menu-bar launcher that on first launch downloads the server release,
  starts it, and starts it on every later launch; it can start/stop the server, open the WebUI and
  check for updates. https://localai.io/docs/getting-started/macos/
- Windows exists only through Docker Desktop/WSL2. The docs' one Windows-specific warning is to keep
  the project on the Linux filesystem or model loading is slow.
  https://localai.io/docs/getting-started/models/

Contrast with EZLM: EZLM is one installer, one scan, one model chosen for you, and a URL and key at
the end (`BETA.md`). LocalAI's first run ends at an empty model list and a gallery the user must
shop in; the user also has to know whether they need the CPU, CUDA 12, CUDA 13, ROCm, Intel or
Vulkan image *before* the first `docker run` (the docs' own table). That is the single biggest
onboarding gap versus EZLM.

Docs drift worth noting: the macOS page (23 Aug 2026) says the DMG and server binary are signed and
notarized and launch with no quarantine prompt, while the README still tells users the DMG is not
signed and to run `sudo xattr -d com.apple.quarantine /Applications/LocalAI.app`, citing issue
#6268 (closed). The README's "Latest News" also stops at 4.11.0 while 4.12.0/4.12.1 are out.

## Hardware detection

- Detection is per model install, not at startup: "When you install a model from the gallery (or a
  YAML file), LocalAI ... detects the required backend and your system's capabilities, then
  downloads the correct version for you". Override with
  `LOCALAI_FORCE_META_BACKEND_CAPABILITY=default|nvidia|amd|intel`.
  https://localai.io/docs/features/gpu-acceleration/
- GPU memory is read from `nvidia-smi` (NVIDIA), `rocm-smi` or, on ROCm 7+, the amdgpu driver in
  sysfs `/sys/class/drm/card*/device/mem_info_*` (AMD), and from the Level Zero driver for Intel,
  where the backend sets `ZES_ENABLE_SYSMAN=1` so an iGPU can report shared memory. The same page
  says LocalAI reads AMD GPU memory "for `/api/resources` and the model fit check".
  https://localai.io/docs/features/gpu-acceleration/
- The macOS/Windows/Linux "scan" is otherwise thin: no CPU feature detection beyond the backend
  image choice, no disk-space gate before a download (the Models page shows free space, but the
  install is not blocked by it).
- Known detection bugs: wrong VRAM value reported (#12058, closed), Intel Arc Pro B70 not detected
  with the Intel image (#9540, closed), gallery sizing ignores registered distributed nodes
  (#11814, open). EZLM's `internal/scan` (per-vendor VRAM, per-app GPU usage on Windows,
  `internal/fit/fit.go` margins) is materially more careful; LocalAI's detection is a backend-tag
  decision plus a free-memory number.

## Model picking

- The gallery (`models.localai.io`, 79 new entries in 4.11.0 alone) is the catalogue. The Models
  page shows a **"Best for this machine"** list, with a precise rule: "GPU recommendations require
  a memory estimate within 95% of the detected model memory budget at a 4096-token context. If none
  of the sampled candidates fit, the recommendation section is hidden." The Home page also omits
  GPU suggestions when nothing fits. https://localai.io/docs/getting-started/models/
- So recommendations are advisory and context-blind: fixed 4096-token assumption, no
  Balanced/Smartest/Fastest preference, no coding-vs-chat distinction. EZLM's
  `internal/fit` + `internal/catalog` ranks per model, per quant, per preference, and models the
  context and batch overhead explicitly.
- The import page is honest about a gap EZLM does not have: "The server returns no preview of the
  model configuration, the size or the memory a model needs before the import starts, so the page
  does not show them. They appear once the import starts."
  https://localai.io/docs/getting-started/models/
- Model identity is a name from the gallery or a YAML file; there is no notion of "the one model
  EZLM picked for you", and no automatic fallback if the pick does not fit (see memory fit below).

## Memory-fit logic

This is where LocalAI is weakest relative to EZLM, and where its issue tracker shows it.

- Fit is checked at **install/recommendation** time (95% of budget at 4096 ctx, above) but not
  enforced at **load** time. The load path applies "hardware auto-tuning" defaults that offload
  everything. A user log in #12081 shows the effective values:
  `effective runtime tuning (override in the model YAML; LOCALAI_DISABLE_HARDWARE_DEFAULTS=true
  disables hardware auto-tuning) ... context=8192 n_batch=512 n_gpu_layers=99999999 parallel="4"
  flash_attention="auto" f16=false`. `n_gpu_layers=99999999` is "offload all layers", not "the
  number of layers that fit". https://github.com/mudler/LocalAI/issues/12081
- The docs still teach manual fitting: `gpu_layers: 22` in the YAML, "Setting it to a high number
  (e.g., `999`) offloads all possible layers", and the OOM troubleshooting is "reduce
  `gpu_layers`", "lower `context_size`", "use Q4_K_M". Nothing computes the number for the user.
  https://localai.io/docs/features/gpu-acceleration/
- Mitigations that do exist: VRAM management that unloads idle models, a dynamic memory reclaimer
  (PR #7583, Dec 2025), automatic multi-GPU model fitting for llama.cpp (PR #7584, Dec 2025), and
  4.12.0's "more control over model memory". https://github.com/mudler/LocalAI#readme
- Consequence in the tracker: "localai cannot run the recommended model" (#12081, open, r1/c6)
  where the gallery-recommended model failed to load and only a full wipe of persistent storage
  fixed it; "Multi-GPU model loading fails with CUDA OOM after Blackwell VRAM/concurrency changes"
  (#10485, closed, c10); "Unbounded `num_ctx` in `/api/chat` and `/api/generate` bypasses
  hardware-aware context-size capping" (#11022, closed).
- EZLM's equivalent is `internal/fit.ComputeBudgets` (10% RAM margin, 8% VRAM on Windows, 12% for
  AMD/Intel Vulkan, OS floor 0.75-2 GB) plus `overhead()`/`batchOverhead`/`specOverhead` and
  `PlansFor`. That is a stricter, per-plan calculation than LocalAI's. EZLM should keep it and
  show it; LocalAI is the cautionary tale for "detect the GPU, then offload everything".

## The OpenAI-compatible server and keys

- Listens on `:8080`. OpenAI-compatible `/v1` (chat, completions, embeddings, images, audio,
  moderations), plus the **Anthropic Messages API** (`/v1/messages`, so Claude Code works), the
  Ollama API (`/api/tags`, `/api/chat`), Open Responses, ElevenLabs and a Realtime WebSocket API.
  https://localai.io/docs/basics/getting_started/ and
  https://localai.io/docs/integrations/
- **Auth is off by default.** "If you configure neither authentication mode, the authentication
  middleware does not restrict requests." The quick-start `docker run -p 8080:8080` publishes the
  port on every interface, so an unconfigured instance is an open OpenAI-compatible endpoint on the
  LAN. https://localai.io/docs/features/authentication/
- Two modes. Legacy: `LOCALAI_API_KEY=sk-...`, comma-separated for several keys, accepted as
  `Authorization: Bearer`, `x-api-key`, `xi-api-key` or a `token` cookie; every key grants **full
  admin** access with no role separation. Multi-user: `LOCALAI_AUTH=true` with SQLite/Postgres,
  admin/user roles, GitHub OAuth or OIDC, per-user keys with `expiresIn`/`paused_until`, usage
  tracking per key. https://localai.io/docs/features/authentication/
- 4.9.0 made auth "deny-by-default" (every route requires credentials unless on an explicit public
  list) and 4.12.1 was a security-only release fixing SSRF in user-supplied URLs (redirect targets
  re-validated per hop, `100.64.0.0/10` and `0.0.0.0/8` treated as non-public).
  https://github.com/mudler/LocalAI/releases/tag/v4.9.0 and
  https://github.com/mudler/LocalAI/releases/tag/v4.12.1
- EZLM by comparison: generated `ezlm-` + 40 base62 chars (`internal/keys/keys.go`), loopback bind
  by default with LAN as an explicit opt-in (`internal/serve/config.go`), named keys with IDs in the
  config. EZLM's default posture is safer; LocalAI has more key lifecycle (expiry, pause, last-used,
  per-key usage) that EZLM lacks.

## Coding-agent integrations

- Documented, per-agent configuration is manual: OpenCode gets a `~/.config/opencode/opencode.json`
  provider block with `baseURL: http://127.0.0.1:8080/v1` (no key in the example, because auth is
  off); Claude Code gets `ANTHROPIC_BASE_URL` + `ANTHROPIC_API_KEY` env vars; Charm Crush gets a
  `~/.config/crush/crush.json`; there are VSCode and JetBrains community plugins.
  https://localai.io/docs/integrations/
- There is also a built-in terminal agent (`local-ai chat`) and MCP support in the server, plus a
  large community list (LangChain, LlamaIndex-style frameworks, Continue-style editors via
  OpenAI-compatible endpoints). https://localai.io/docs/integrations/
- The friction is the same as everywhere in LocalAI: the user edits JSON or exports env vars. EZLM
  writes the OpenCode/Hermes config and can open the app already pointed at the server (`BETA.md`),
  which is strictly better for a one-click product.
- Context limits are the user's problem: the OpenCode example hard-codes `context: 38000` and
  `output: 65536` by hand. A wrong number here is a silent truncation or a server-side overflow.

## Update mechanism

- Containers: pull a new image tag and recreate. The docs warn that files not on the four volumes
  (`/models`, `/backends`, `/configuration`, `/data`) "are lost when the container is recreated
  during an image upgrade", and that `/backends` may be a stale copy if it is a mounted volume.
  https://localai.io/docs/installation/containers/
- That stale-backend path is a real failure, not theory: in #12081 the maintainer-bot traced a
  model-load failure to `InstallBackendFromGallery` returning early when a runnable backend with the
  same name is already installed (`core/gallery/backends.go:197-210`), so a mounted `/backends`
  directory can keep an old llama.cpp forever. The reporter only fixed it by deleting all
  persistent storage. https://github.com/mudler/LocalAI/issues/12081
- macOS launcher has "check for updates" in the menu bar; Linux binary users download a new binary.
  No delta updates, no signature/verification step in the UI for container users.
- Cadence is fast and occasionally breaking: 4.9.0 (2026-08-20), 4.10.0 (09-17), 4.11.0 (10-02),
  4.12.0 (10-22), 4.12.1 (10-23); 4.11.0 alone was "243 merged pull requests, 353 commits".
  4.12.x then regressed the backend download path (#12893, `mkdir //downloading: permission denied`,
  open, r1/c2). https://github.com/mudler/LocalAI/releases
- EZLM's update story (one click, verifies, reopens, keeps the model running, `BETA.md`) is a
  genuine advantage. The LocalAI lesson is the volume/backend-version trap: an updater must own the
  engine binaries and models, not leave them in user-managed directories.

## Most common user complaints

Counting method: GitHub search API, `repo:mudler/LocalAI is:issue` with the given terms, sorted by
`reactions`, on 2026-11-06; the repo had 50,229 stars and 181 open issues+PRs at that moment. For
each topic I list the issue's own reaction total and comment count, not a sum across duplicates.
Discord/Reddit were not mined (no reliable public counts without an account), so this is a
GitHub-only sample and probably under-represents non-developer users.

1. **No native Windows build** - #2368 "Native windows version?" open since 2024-05-22, **r16/c7**,
   the most-reacted open issue in the repo by a wide margin (next open issue has 7).
   https://github.com/mudler/LocalAI/issues/2368
2. **AMD/ROCm is hard** - #1592 "Better Support for AMD and ROCM via docker containers", closed,
   **r2/c78**, by far the longest GPU thread. The docs still list only a handful of verified devices
   (llama.cpp: MI100, MI210/250, gfx1151) and say ROCm 6.4 dropped gfx803/900/906 from rocBLAS.
   https://github.com/mudler/LocalAI/issues/1592
3. **Backend and model installs break** - #12893 `mkdir //downloading: permission denied` (4.12.1,
   open, r1/c2), #12807 "Can't create folders to download models" (open), #11995 gallery model
   fails to install with a SHA mismatch "reproducible across retries" (open), #12081 recommended
   model will not run (open, r1/c6). https://github.com/mudler/LocalAI/issues/12893
4. **OOM / wrong VRAM numbers** - #10485 multi-GPU CUDA OOM after Blackwell changes (closed, c10),
   #12058 GPU RAM detection with an incorrect VRAM value (closed), #11022 unbounded `num_ctx`
   bypasses hardware-aware capping (closed). https://github.com/mudler/LocalAI/issues/10485
5. **macOS installer breakage** - #6268 "v3.5.0 MacOS installer is broken on Apple M series",
   closed, **r8/c10**. The README still carries the quarantine workaround.
   https://github.com/mudler/LocalAI/issues/6268
6. **Docs drift** - the signing contradiction above, and the README's news list lagging the actual
   releases. Minor on its own, but it is the kind of thing a beta user hits in the first ten
   minutes.

## Windows on Arm and AMD/Intel GPUs

**Windows on Arm.** No native Windows anything, so WoA means Docker Desktop's ARM64 Linux VM plus
WSL2. LocalAI publishes arm64 Linux images (Apple Silicon, NVIDIA Jetson L4T, DGX Spark) but no
Windows ARM64 binary and no page that mentions Snapdragon. There is no CUDA on WoA, so a WoA user
would land on the Vulkan or CPU image inside a container, with the container's own driver stack. The
docs' only Windows note is "ensure the project is on the Linux filesystem to avoid slow model
loading", i.e. the WSL2 bind-mount penalty. NPU support in the backend list is RKLLM (Rockchip);
no Qualcomm Hexagon backend appears. https://localai.io/docs/installation/containers/ and
https://localai.io/docs/features/gpu-acceleration/

**AMD.** ROCm only, Linux host only, container recommended. The verified list is short (llama.cpp on
MI100/MI210/MI250 and Strix Halo gfx1151; diffusers on MI100/MI210/250; whisper, coqui,
transformers and vllm "no"). Strix Halo needs kernel boot parameters
(`iommu=pt amdgpu.gttsize=126976 ttm.pages_limit=32505856`), four environment variables
(`HSA_OVERRIDE_GFX_VERSION=11.5.1`, `ROCBLAS_USE_HIPBLASLT=1`, `HSA_XNACK=1`, `HSA_ENABLE_SDMA=0`)
and a warning not to set `GGML_CUDA_ENABLE_UNIFIED_MEMORY`. Consumer RDNA3/RDNA4 cards are in the
build target list (gfx1030, gfx1100-1102, gfx1200/1201) but not in the "verified" table. That is a
lot of tribal knowledge for a beta user; EZLM's job is to encode it.

**Intel.** SYCL images with the driver carried in the image; `mmap: true` has a known hang; iGPU
memory is only visible with `ZES_ENABLE_SYSMAN=1`; newer cards need
`ZE_ENABLE_ALT_DRIVERS=<host libze_intel_gpu.so.1>`. #9540 (Arc Pro B70 not detected, closed) and
#11077 (B70 support request) show the detection edge. Vulkan is the vendor-neutral fallback and is
documented as such ("the fallback when no matching CUDA, ROCm, or Intel image is available").

## LocalAI vs EZLM, dimension by dimension

| Dimension | LocalAI 4.12.1 | EZLM (snapshot 2026-11-06) |
|---|---|---|
| First run | `docker run`, then shop in a gallery; image tag chosen by hand | one installer, scan, auto-pick, URL + key |
| Hardware detection | backend tag per model; GPU memory from vendor tools; no disk gate | `internal/scan` per-vendor VRAM, per-app GPU use, disk |
| Model picking | gallery + "Best for this machine", 95% of budget at 4096 ctx, hidden if nothing fits | `internal/fit` + `internal/catalog`, per-quant, per-preference ranking |
| Memory fit | advisory at install, `n_gpu_layers=99999999` at load, manual YAML | computed budgets with margins, overheads, plan ranking |
| Server/keys | `:8080`, OpenAI + Anthropic + Ollama APIs, auth off by default, admin-only legacy keys | `:8080`, OpenAI API, generated key, loopback default, named keys |
| Coding agents | documented manual JSON/env edits for OpenCode, Claude Code, Crush | writes config, opens OpenCode/Hermes |
| Updates | pull image, recreate, four volumes, stale-backend trap | one click, verifies, keeps models |
| Windows | Docker/WSL2 only; no native build (top open issue) | native installer, incl. Windows on Arm |
| AMD/Intel | ROCm/SYCL images, narrow verified list, vendor env-var rituals | Vulkan path with Windows-specific VRAM margins |

## Recommendations for EZLM

**R1. Show the fit decision before the download, not after it. Priority: high. Effort: S.**
Evidence: LocalAI's gallery has no pre-import size/memory preview ("The server returns no preview of
... the size or the memory a model needs before the import starts"), its recommendation is a hidden
or shown list rather than a check, and users end up with a recommended model that will not run
(#12081). EZLM already computes `PlansFor`/`Budgets`; surface the chosen plan as "X GB of Y GB,
context N" in the install screen and on the model card, and refuse a model that cannot fit at the
selected context instead of downloading 20 GB first. This is the cheapest way to convert EZLM's
stronger planner into visible trust.

**R2. Add a "why this model" panel and a per-model override. Priority: medium. Effort: S.**
Evidence: LocalAI logs its effective runtime tuning and offers
`LOCALAI_DISABLE_HARDWARE_DEFAULTS=true` to turn it off, which is the only way a user learns why a
model offloaded all layers (#12081). EZLM's `internal/fit` picks layers, context and quant but the
user never sees the numbers. Expose the chosen `gpu_layers`/context/quant and let the user pin one
value (e.g. "fit to 8k context") while keeping the automatic default. Small UI, high support value,
and it gives the beta a concrete answer to "why did you pick this model".

**R3. Make the updater own the engine, and repair stale backends. Priority: high. Effort: M.**
Evidence: LocalAI's container upgrade loses anything not on four volumes and can keep an old backend
binary from a mounted `/backends` directory; the reporter in #12081 only recovered by deleting all
persistent storage, and 4.12.x regressed the backend download path (#12893). EZLM already keeps
models across updates and restarts them; add (a) an engine/backend version recorded next to the
model, (b) a "repair" action that re-downloads a mismatched engine, and (c) a post-update smoke
request against `/v1/models` before declaring success. EZLM's `internal/update` is the place.

**R4. Keep auth on by default, and add the key lifecycle LocalAI has. Priority: high. Effort: S.**
Evidence: LocalAI is unauthenticated by default and its legacy key grants full admin
(https://localai.io/docs/features/authentication/); it took until 4.9.0 to become deny-by-default
and 4.12.1 was a security-only SSRF fix. EZLM's generated `ezlm-` key and loopback default are the
right posture. Add what LocalAI got right: last-used time, per-key usage counts, pause/revoke, and
an expiry option, and make "expose on LAN" impossible without a key. This also gives EZLM's key
screen something to show beyond a copy button.

**R5. Treat "no Docker, and it works on Windows on Arm" as the headline differentiator. Priority:
high. Effort: S (positioning + one test pass), M if WoA needs a Vulkan fallback fix.**
Evidence: the most-reacted open issue in LocalAI is a 2024 request for a native Windows version
(#2368, r16/c7, still open), and the project's Windows story is Docker Desktop/WSL2 with a
Linux-filesystem warning. EZLM already ships a native Windows installer and claims ARM laptops in
`BETA.md`. Verify the WoA path with no CUDA (Vulkan/CPU, and the `internal/fit` Windows margins
already account for Vulkan's looser free-VRAM accounting), then say plainly in the installer and
the site: no Docker, no WSL, works on Snapdragon. It is the one claim LocalAI cannot copy quickly.
